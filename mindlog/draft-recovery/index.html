MindLog에서 일기를 쓰고 분석하는 과정

MindLog는 일기를 쓰면 AI가 감정 상태와 위로 메시지·행동 제안을 돌려주는 모바일 앱입니다. 사용자는 글을 쓰고 날짜·사진을 고른 뒤 분석을 요청하고, 저장된 일기와 감정 기록을 다시 볼 수 있습니다. Flutter는 모바일 화면을 만들고, Riverpod은 조회·분석 같은 처리 상태를 화면에 연결합니다. 완성된 일기는 기기 안의 데이터베이스인 SQLite에 저장하며, AI 분석 요청은 외부 서비스인 Groq로 전송합니다. 서비스·기술의 근거

이 사건에서는 화면에 입력된 내용과 앱을 다시 열어도 남는 저장 내용이 다르다는 점이 중요합니다. 입력란에 글이 보여도 기기에 기록하기 전에 앱이 종료되면 다시 불러올 수 없습니다. 임시저장, 즉 초안 보관은 분석을 요청하기 전의 글·날짜·사진 선택을 이어 쓰게 하는 별도 경로입니다.

제출 뒤 저장으로는 작성 중인 글을 지킬 수 없었다

일기를 쓰다가 다른 앱을 보거나 뒤로가기를 눌렀다고 생각해 봅시다. 이 상황은 문제를 이해하기 위한 사용 예시입니다. 변경 전에는 분석을 위해 제출한 뒤에야 일기를 분석 대기 상태인 pending으로 저장했습니다. 그전에 작성 화면을 나가거나 운영체제가 앱을 종료하면 쓰던 글과 사진 선택을 잃을 수 있었습니다. 제출 이후의 저장이 있어도 사용자가 글을 쓰는 동안은 보호하지 못했던 것입니다. 당시 문제와 변경 기록

해결해야 할 범위는 제출 전 초안 한 건이었습니다. 그래서 작은 데이터를 기기에 보관하는 SharedPreferences에 본문·작성 날짜·마지막 저장 시각·사진 경로를 묶어 저장했습니다. JSON은 이 항목들을 하나의 문자열로 표현하는 형식입니다. 기존 일기 DB에 초안용 표를 추가하고 저장 구조를 바꾸는 비용을 피하려는 선택이 당시 기록과 저장 구현 커밋에 남아 있습니다. 여러 초안을 쌓아 두는 기능이나 초안의 암호화·잠금번호 보호까지 제공하는 선택은 아닙니다. 선택 근거와 범위

제출할 때의 최소 10자 조건도 초안에는 적용하지 않았습니다. 예를 들어 9자만 쓰고 떠나도 그 글은 보관할 필요가 있기 때문입니다. 본문 앞뒤의 공백을 정리한 뒤 글과 사진이 모두 비면 기존 초안을 지우고, 사진만 있으면 사진 경로를 포함해 보관합니다. 날짜만 고른 빈 폼은 초안으로 남기지 않습니다. 초안 저장 조건

입력 중에는 잠시 기다리고 떠날 때는 바로 저장하기

글자 하나를 칠 때마다 기기에 쓰는 대신, 입력이 800ms, 즉 0.8초 동안 멈추면 저장하도록 했습니다. 이를 디바운스라고 합니다. 새 글자가 들어오면 앞서 잡은 대기를 취소하고 다시 기다려, 연속 입력 중의 쓰기 요청을 줄이는 방식입니다. 0.8초는 설정한 대기시간이며 측정한 성능 개선율이 아닙니다.

그 대기만 사용하면 입력 직후 떠나는 경우를 놓칩니다. 따라서 화면 이탈이나 앱이 뒤로 가는 전환에서는 대기를 건너뛰고 현재 값을 저장하도록 연결했습니다. 코드의 flush는 이 즉시 저장 요청을 뜻합니다.

날짜 변경·사진 추가 또는 제거 바뀐 본문·날짜·사진 경로를 바로 저장 요청

PopScope는 화면을 나가려는 동작을 받는 장치이고, AppLifecycleListener는 앱이 앞에 보이는지 뒤로 갔는지를 받는 장치입니다. 둘을 통해 입력 타이머와 실제 사용자의 이탈 시점을 연결했습니다. 다만 저장을 요청하는 것과 운영체제가 강제로 종료하기 전에 저장이 완료되는 것은 다릅니다. 모든 종료 조건의 무손실 보장으로 설명하지 않습니다. 저장 시점 명세, 화면 연결 코드

다시 들어올 때 빈 화면이 기존 초안을 덮지 않게 하기

변경 후 기본 동선은 다음과 같습니다. 아래 도식은 기준 코드의 정상적인 보관·복원 흐름이며, 저장 실패·강제 종료까지 성공을 보장하는 그림은 아닙니다.

작성 화면에 처음 들어오면 입력란은 비어 있고, 기존 초안은 기기에서 읽어 오는 중입니다. 이때 빈 입력란을 먼저 저장하면 앞서 보관한 초안이 지워질 수 있습니다. 그래서 DiaryDraftController, 즉 초안 복원·저장을 관리하는 코드가 조회 중에는 저장을 잠그고 조회가 끝난 뒤에 허용합니다. 이 잠금은 입력란을 못 쓰게 막는 기능이 아니라 저장 요청을 막는 처리입니다. 복원과 저장 잠금 구현

복원할 초안이 있으면 본문·날짜·사진 경로를 입력 화면에 반영하고 복원 안내 배너를 보여 줍니다. 날짜가 화면에 들어온 날보다 미래라면 그날로 조정합니다. 복원 조회가 실패한 경우에는 실패를 기록하고 ‘초안 없음’ 상태로 전환해, 이후 새 입력의 자동저장이 계속 잠기지 않도록 했습니다. 이것이 기존 초안 복원 성공을 뜻하는 것은 아닙니다. 화면 반영

여기에는 남은 결함도 있습니다. 기존 초안을 지키는 잠금만으로 복원 중 새로 친 글까지 보호되지는 않습니다. 기준 코드에서는 조회 중에도 입력란에 글을 쓸 수 있고, 뒤늦게 도착한 기존 초안을 입력란에 통째로 반영하므로 그 사이의 새 글이 덮일 수 있습니다. ‘기기에 있던 초안은 남는다’와 ‘사용자의 새 입력이 보존된다’를 구분해야 합니다. 당시 문서의 <50ms는 이번에 측정한 값이 아니며, 현재 공개 빌드의 재현 결과로도 사용하지 않습니다. 남은 입력 경합의 근거

저장과 삭제가 엇갈려 지운 초안이 되살아나지 않게 하기

자동저장을 넣으면 사용자가 글을 바꾸거나 지울 때 이미 기다리던 요청이 남을 수 있습니다. 예를 들어 저장 요청 뒤에 삭제를 했는데, 앞선 저장이 더 늦게 끝나면 지운 초안이 다시 생길 위험이 있습니다. 이는 처리 요청과 완료 시점이 어긋나는 순서 문제입니다.

기준 컨트롤러는 두 가지를 함께 사용합니다. 첫째, _operationTail은 저장·폐기 작업을 한 줄로 이어 앞선 작업이 끝난 뒤 다음 작업을 실행합니다. 이미 시작한 저장이 있다면 폐기가 그 뒤에 오게 합니다. 둘째, _revision은 변경마다 붙이는 순번입니다. 아직 실행 전인 오래된 저장은 최신 순번과 다르면 건너뜁니다. 폐기할 때에는 입력 타이머를 취소하고 순번을 바꾸며, 폐기 중 새 저장도 막습니다. 작업의 실행 순서와 요청의 유효성을 함께 다루는 것입니다. 저장·폐기 순서 구현

이 순번은 복원 중 입력 덮임까지 해결하는 장치는 아닙니다. 복원 중에는 새 입력의 저장 요청 자체를 받지 않으므로 앞 절의 한계가 남습니다. 서로 다른 문제를 같은 ‘입력 보호 완료’로 묶지 않습니다.

사진은 경로와 파일을 함께 보관해야 했다

초안에 사진의 위치인 경로를 적는 것만으로 사진이 보존되지는 않습니다. 사진 선택기가 돌려준 파일은 운영체제의 임시 보관 공간에 있어, 다음 실행 때 사라질 수 있기 때문입니다. 그래서 사진을 고르면 앱의 __draft__ 폴더로 복사하고, 그 복사본 경로를 초안에 넣도록 했습니다. 사진 파일은 폴더에, 그 위치는 SharedPreferences의 초안에 저장하는 두 부분이 이어져야 복원할 수 있습니다. 사진 복사·제거 코드

후속 변경에서는 사진을 지웠다가 다시 넣을 때 파일명이 겹치는 문제도 다뤘습니다. 현재 사진 개수로 다음 파일 번호를 정하면 삭제 뒤 번호를 재사용해 남아 있는 사진을 덮을 수 있습니다. 번호를 계속 증가시키고, 복원 후에도 기존 파일의 가장 큰 번호 다음부터 이어 쓰도록 보완했습니다. 초안 사진을 제거할 때는 앱의 초안 복사본을 정리하고, 복사 실패 때 대신 사용한 원래 경로의 파일은 지우지 않도록 구분했습니다. 이미지 후속 수정
