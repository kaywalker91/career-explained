고객의 디자인이 인쇄 파일이 되기까지

PLLI LAB은 고객이 꾸민 디자인을 실제 상품 제작에 사용할 수 있도록 연결하는 맞춤형 인쇄 플랫폼입니다. 고객이 사진·글자·스티커로 상품을 꾸미면, 제작 담당자와 디자이너는 그 디자인에 맞는 인쇄 이미지를 받아 다음 제작 작업을 진행해야 합니다. 화면에 디자인이 보이는 것만으로 인쇄 파일이 준비된 것은 아닙니다. 각 요소를 정해진 크기와 위치로 그려 파일로 저장하는 과정이 필요합니다. 이 이미지 생성 작업을 렌더링이라고 합니다. 서비스와 기술의 근거

인쇄 파일을 오래 기다리거나 받지 못하는 문제를 인계받았다

인계받은 개선 요청에는 이벤트 기간 디자인 1,700건 이상을 다뤄야 하는 상황과, 파일을 받으려다 1시간 넘게 기다리거나 Chrome이 STATUS_BREAKPOINT 오류로 종료된 사례가 적혀 있었습니다. 제작 담당자와 디자이너에게 필요한 것은 화면에 보이는 디자인을 실제로 쓸 수 있는 인쇄 파일로 받는 일이었습니다. 이미지 생성이 중단되면 다음 제작을 준비하기도 어려워집니다. 1,700건과 대기 시간은 당시 보고된 사례이며, 제가 같은 조건에서 전후 속도를 측정한 값은 아닙니다. 인계받은 문제

저는 이 렌더링 문제를 인계받아 AI와 함께 문제 해결 전반을 직접 진행했고, 주요 변경은 사전에 질의하고 승인을 받아 수행했습니다. 아래는 그중 여러 주문의 이미지를 차례로 만들고, 도중에 멈춰도 이어 처리하도록 바꾼 과정입니다. 이 전체 역할은 사용자 확인 내용입니다. 개별 코드의 단독 설계·작성 여부와 사건별 시험·배포 분담은 추가 확인이 필요합니다. 본인 역할의 확인 범위

멈춘 이유를 알아야 남은 주문을 이어 갈 수 있었다

기존에는 이미지 생성 기능이 한 주문 단위로 움직였고, 이를 호출한 화면에서는 처리가 끝났다는 것만으로 성공과 실패를 구분하기 어려웠습니다. 여러 주문을 연속으로 그릴 때 브라우저의 작업용 메모리가 한계에 닿아 이미지 생성 엔진이 멈추는 문제도 기록돼 있었습니다. 메모리는 작업 중인 내용을 잠시 올려놓는 공간입니다. 당시 기록에서 힙(heap)은 이 작업에 쓰이는 메모리 공간을 가리킵니다. 04-06 업무요약, §1~2

여러 주문을 하나의 목록으로 받아 처리하는 배치 구조를 만들면서, 다음 행동을 정할 수 있도록 결과도 나눴습니다. 이미지를 다 만들었으면 다음 대상을 처리하고, 메모리 사용량이 정한 한계에 닿았으면 진행을 남긴 뒤 새로고침하는 식입니다. 사용자가 취소한 경우와 이미지 생성 엔진 자체가 실패한 경우도 완료와 구분했습니다. 이 네 가지 결과를 코드에서 구별해 전달하는 장치가 RenderResult입니다. 실패를 모두 자동으로 해결하는 기능이 아니라, 화면이 중단 이유에 맞게 대응할 수 있게 한 변경입니다.

작업 수 제한과 탭 잠금은 서로 다른 중복을 막는다

한 탭 안에서는 여러 이미지 캡처가 한꺼번에 실행되지 않도록 처리 순서를 정했습니다. Semaphore는 동시에 작업할 수 있는 수를 제한하는 장치이며, 여기서는 하나의 렌더링 대기열로 차례로 처리하는 데 사용했습니다. 작업이 겹치면서 생기는 충돌과 메모리 부담을 관리하는 구조입니다. 이는 당시 구현 기록으로 설명한 작동 원리이며, 여러 기술을 비교한 뒤 제가 이 방식을 골랐다는 당시 발언을 새로 보탠 것은 아닙니다.

하지만 관리자가 같은 웹을 두 탭에서 열면, 각 탭이 자기 순서를 지켜도 같은 작업을 따로 시작할 수 있습니다. 그래서 Web Lock으로 같은 브라우저에서 같은 웹의 배치 작업을 한 탭만 실행하도록 했습니다. 한 탭 내부의 순서를 정하는 것에 더해, 탭 사이에서도 실행 권한을 조정한 것입니다. 이 잠금의 범위는 같은 브라우저의 같은 웹 출처이며, 다른 PC에서 시작한 작업까지 조정하지는 않습니다. 여러 탭의 저장 충돌은 당시 기록에 적힌 위험으로 설명합니다. 작업 수 제한과 탭 잠금, §1~2

배치 시작 때 필요한 스티커 이미지를 미리 읽고 함께 사용하도록 한 것도 같은 이미지를 주문마다 반복해서 요청하는 부담을 줄이는 변경이었습니다. 다만 이미지를 미리 읽는 처리와 최종 인쇄물에 모든 요소가 들어갔는지 확인하는 일은 따로 필요했습니다. 후속 누락 검증은 PLLI-006에서 이어 설명합니다.

진행 정보를 남겨 새로고침 뒤 이어 처리하기

순서대로 그려도 긴 작업이 끝날 때까지 메모리가 충분하다는 보장은 없습니다. 그래서 메모리 한계 신호를 받으면 어떤 작업을 이어 해야 하는지 보관하고, 같은 탭을 새로고침한 뒤 남은 처리를 이어 가도록 했습니다. 한 번 연 페이지 안에서 모든 주문을 끝내려 하기보다 페이지를 다시 시작할 수 있게 하고, 그 사이에 진행 정보가 사라지지 않도록 연결한 것입니다.

진행 정보는 같은 탭의 새로고침 뒤에도 읽을 수 있는 SessionStorage에 저장했습니다. 이미지 파일 자체를 넣는 곳이 아니라 재개에 필요한 정보를 남기는 곳입니다. 화면에 다시 들어왔을 때 저장한 지 30분 이내인 정보가 있으면 자동으로 재개하도록 구현했습니다. 이 30분은 진행 정보를 유효하게 볼 기간입니다. 복구에 걸린 시간이 아니며, 탭을 닫으면 지워지는 저장 공간이므로 다른 기기나 탭 종료 뒤의 영구 복원까지 지원하는 방식도 아닙니다. 진행 보관·재개 기록, §2

새로고침 뒤에는 저장한 위치만 읽어서는 충분하지 않았습니다. 주문을 읽을 권한을 가진 로그인 정보가 먼저 복원돼야 하고, 이전 작업이 끝났는데 남은 잠금도 정리해야 했습니다. 4월 8일에는 로그인 복원을 기다리고, 방치된 잠금을 정리하며, 처리 직전에 최신 주문 상태를 다시 읽는 보완이 이어졌습니다. 새 페이지에서도 처리할 준비를 갖추는 과정까지 필요했던 것입니다. 이 방식은 진행 정보의 유효 시간·잠금·주문 상태를 함께 관리해야 하는 비용이 있으며, 진행을 남길 틈도 없는 갑작스러운 브라우저 종료까지 모두 복구한다는 보장은 아닙니다. 04-08 후속 보완, §2~4

아래는 당시 기록의 주요 처리 관계를 묶은 그림입니다. 모든 오류 분기나 현재 코드의 실행 결과를 재현한 그림은 아닙니다.

이미 만든 결과를 다운로드에서 다시 사용하기

작업을 이어 가는 것과 함께, 앞서 만든 이미지를 실제 다운로드에서도 활용하도록 바꿨습니다. 기존 다운로드 경로는 사전 렌더링 결과가 있어도 이미지를 다시 그리고 있었습니다. 주문에 저장한 이미지 주소를 먼저 확인하고, 이미 만든 결과가 있으면 그 파일을 사용하도록 고쳤습니다. 같은 계산을 반복하지 않고 앞선 결과를 쓰는 캐시 재사용입니다. 기존 결과 재사용, §3

여기서는 두 종류의 저장을 구분해야 합니다. SessionStorage의 진행 정보는 새로고침 뒤 무엇을 이어 할지 알려 줍니다. 완성한 이미지 파일은 Storage라는 파일 보관 서비스에 두고, 어느 주문의 파일인지 찾을 주소는 주문 정보를 보관하는 데이터베이스인 Firestore에 남깁니다. 다운로드 때 이 주소를 쓰면 이미지를 다시 만드는 과정은 생략할 수 있지만 파일을 전송받는 시간은 여전히 필요합니다. 당시 자료로 같은 조건의 다운로드 속도 개선율을 확정하지는 못했습니다.

중단된 주문을 이어 처리했지만 이미지 품질 문제는 남았다

4월 6일 업무요약에는 배치 처리와 진행 복원, 결과 재사용을 구현한 내용이 남아 있습니다. 다만 흰 배경·처리 건너뛰기·이미지 주소 개수·다운로드의 수동 시험 대기 상태도 함께 기록돼 있습니다. 뒤에 성공 사례가 나왔다고 해서 이 날짜의 시험을 소급해 통과한 것으로 바꾸지는 않습니다. 당시 구현과 남은 시험, §1~3·미해결 항목
