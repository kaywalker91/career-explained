고객의 디자인이 인쇄 파일이 되기까지

PLLI LAB은 고객이 꾸민 디자인을 실제 상품 제작에 사용할 수 있도록 연결하는 맞춤형 인쇄 플랫폼입니다. 고객이 사진·글자·스티커로 상품을 꾸미면, 제작 담당자와 디자이너는 그 디자인에 맞는 인쇄 이미지를 받아 다음 제작 작업을 진행해야 합니다. 화면에 디자인이 보이는 것만으로 인쇄 파일이 준비된 것은 아닙니다. 각 요소를 정해진 크기와 위치로 그려 파일로 저장하는 과정이 필요합니다. 이 이미지 생성 작업을 렌더링이라고 합니다. 서비스와 기술의 근거

이 프로젝트의 관리자 웹은 Flutter Web과 Dart로 만들었습니다. Flutter Web은 브라우저에서 화면을 구성하는 도구이고, CanvasKit·WebGL은 디자인을 그리는 데 사용하는 기술입니다. 만들어진 이미지 파일은 Storage에 보관하고, 어느 주문의 어느 이미지인지 가리키는 주소 등은 주문 정보를 보관하는 Firestore에 기록합니다. 따라서 고객 디자인 → 브라우저에서 이미지 생성 → 파일과 주소 저장 → 제작용 다운로드라는 흐름을 함께 봐야 합니다.

많은 주문을 받았을 때 기다림과 중단이 제작 업무로 이어졌다

인계받은 개선 요청에는 이벤트 기간 디자인 1,700건 이상, 1시간 넘는 대기, Chrome의 STATUS_BREAKPOINT 종료가 보고돼 있습니다. 이는 당시 작업자가 보고한 사례이며, 같은 환경에서 전후 속도를 측정한 값은 아닙니다. 파일을 받아야 다음 제작 단계로 갈 수 있으므로 이미지 생성 중단은 웹 화면 안의 문제를 넘어 제작 준비를 막는 문제였습니다. 당시 업무 부담과 요청

4월 6일 업무요약은 기존 엔진이 한 주문 단위로 동작했고, 호출한 쪽에서 결과를 명확히 구분하기 어려웠다고 설명합니다. 여러 주문을 연속으로 그리면 브라우저의 작업용 메모리인 힙 사용량이 한계에 이르고, 이미지 생성 엔진이 더는 처리하지 못하는 상황도 기록돼 있습니다. 여러 탭이 같은 작업을 동시에 시작하면 결과 저장이 충돌할 위험도 있었습니다. PLLI-001 사건 원본 · 04-06 업무요약, §1~2

해결해야 할 조건은 주문을 여러 개 받되 이미지 생성이 한꺼번에 겹치지 않게 하고, 중단 이유를 알아 다음 행동을 정하며, 새로고침 뒤에도 진행을 이어 가는 것이었습니다. 배치는 여기서 여러 주문을 하나의 처리 목록으로 받아 차례로 진행한다는 뜻입니다.

완료와 중단 이유를 구분해야 다음 행동을 정할 수 있었다

호출한 화면이 단순히 “함수가 끝났다”는 사실만 알면, 이미지를 저장한 것인지 메모리 때문에 멈춘 것인지 판단하기 어렵습니다. 그래서 엔진이 처리 결과를 정해진 종류로 돌려주도록 바꿨습니다. 당시의 RenderResult는 이 결과를 표현하는 코드 구조입니다.

04-06에 기록된 결과 일상적인 뜻과 구분하는 이유
RenderCompleted 해당 처리를 완료함. 다음 대상을 진행하는 근거가 됨
RenderHeapThreshold 메모리 사용량이 설정한 한계에 도달함. 진행 보관·새로고침·재개로 연결할 수 있는 신호
RenderCancelled 사용자가 취소함. 정상 완료와 구분해야 함
RenderEngineDeath 이미지를 그리는 엔진이 실패함. 정상 완료나 사용자의 취소와 구분해야 함

이 구분은 엔진이 스스로 모든 실패를 해결한다는 뜻은 아닙니다. 호출한 쪽이 상황별 후속 처리를 할 수 있게 만든 것입니다. 후속 분석에 등장하는 품질 저하 저장 상태 RenderDegraded까지 4월 6일의 네 가지 결과에 소급해 넣지 않습니다. 결과 타입의 당시 기록, §1 · 후속 상태 분류

작업 수 제한과 탭 잠금은 서로 다른 중복을 막는다

한 탭 안에서는 Semaphore로 동시에 캡처할 수 있는 작업 수를 제한해 단일 렌더링 대기열로 처리하도록 했습니다. Semaphore는 작업을 시작할 수 있는 자리를 제한하는 장치입니다. 이 사건에서는 여러 캡처를 겹쳐 실행하지 않고 순서대로 진행하는 역할입니다. 동시에 더 많이 처리해 속도를 높이는 선택이 아니라, 메모리 부담과 작업 간 충돌을 관리하려는 구조로 읽을 수 있습니다. 이는 기록된 변경을 바탕으로 한 원리 설명이며 본인의 당시 발언을 인용한 것은 아닙니다.

별개의 문제로, 관리자가 같은 웹을 두 탭에서 열면 각 탭 안의 대기열만으로는 다른 탭의 실행을 조정할 수 없습니다. 그래서 Web Lock을 사용해 여러 탭이 같은 배치 작업을 동시에 실행하지 않도록 했습니다. Web Lock은 같은 브라우저의 같은 웹 출처에서 이름 붙인 작업의 실행 권한을 조정하는 기능입니다. 다른 PC에서 같은 계정을 쓰는 경우까지 서버 전체를 잠그는 기능으로 설명하지 않습니다. 작업 수 제한·탭 잠금 기록, §1~2

스티커 이미지는 배치 시작 때 미리 읽어 함께 사용하도록 했습니다. 필요한 이미지를 매 주문마다 반복해서 요청하는 부담을 줄이려는 변경입니다. 다만 미리 읽었다는 사실만으로 최종 인쇄 이미지에 모든 스티커가 들어갔다고 판정할 수는 없습니다. 실제로 후속에는 빈 이미지와 누락 검증을 계속 다뤘습니다. 미리 읽기 기록, §1 · 후속 재발

진행 정보를 남겨 새로고침 뒤 이어 처리하기

차례대로 처리해도 긴 작업 내내 메모리 사용이 안정적이라는 보장은 없습니다. 4월 6일 기록에서는 메모리 한계 신호를 받으면 진행을 보관하고 페이지를 새로고침한 뒤 이어 처리하는 구조를 추가했습니다. 한 번 로드된 페이지 안에서 처리하던 구간을 끝내고, 새 페이지에서 남은 처리를 시작하는 것입니다.

여기서 SessionStorage는 같은 탭의 페이지가 새로고침돼도 읽을 수 있는 브라우저 저장 공간입니다. 이미지 파일 자체를 넣는 곳이 아니라, 무엇을 이어 처리할지 판단하는 진행 정보를 보관합니다. 당시 기록은 pod_render_resume라는 항목을 두고 화면 진입 때 확인해 30분 이내 정보라면 자동 재개하도록 했다고 설명합니다. 30분은 구현한 유효 시간이며 복구에 걸린 시간이나 성능 측정값이 아닙니다. 탭 종료 때 지워지는 저장 공간이므로 브라우저를 닫거나 다른 기기로 옮긴 뒤에도 영구 복원된다고 설명하지 않습니다. 진행 보관·재개 기록, §2

아래 도식은 당시 기록의 주요 처리 관계를 압축한 것입니다. 모든 오류의 상세 분기나 현재 코드 실행을 재현한 그림은 아닙니다.

진행 복원에는 새 페이지에서 주문을 읽고 작업 권한을 되찾는 과정도 필요합니다. 후속 4월 8일 기록에는 로그인 정보가 복원될 때까지 기다리기, 정상 작업이 끝났는데 남은 잠금 정리, 최신 주문 상태 다시 읽기 등의 보완이 있습니다. 따라서 4월 6일의 저장 공간 추가만으로 이후의 재개 성공 전체를 설명하지 않습니다. 04-08 후속 구현, §2~4 · 구현과 실행 경과의 대조

이 방식에는 진행 정보의 유효 시간, 잠금 해제, 재진입 때의 주문 상태를 함께 관리해야 하는 비용이 있습니다. 또한 진행을 보관할 수 있는 메모리 한계 대응과 예고 없는 브라우저 강제 종료는 같은 조건이 아닙니다. 모든 강제 종료에서 진행을 지킨다는 보장으로 확대하지 않습니다.

이미 만든 결과를 다운로드에서 다시 사용하기

배치에서 이미지를 미리 만들어도 다운로드 버튼이 매번 처음부터 그리면 앞선 결과를 활용하지 못합니다. 그래서 주문에 저장된 인쇄 이미지 주소 목록인 printUrlsByIndex를 다운로드 경로에서 확인하고, 사전 렌더링 결과가 있으면 다시 그리지 않고 사용하도록 바꿨습니다. 이를 캐시 재사용이라고 합니다. 같은 계산을 반복하는 대신 앞서 만든 결과를 쓰는 방식입니다. 결과 재사용 기록, §3

이때 SessionStorage의 진행 정보와 Firestore의 결과 주소는 역할이 다릅니다. 앞의 것은 새로고침 뒤 무엇을 이어 할지 알려 주고, 뒤의 것은 이미 만들어 Storage에 보관한 파일을 찾게 해 줍니다. 주소를 곧바로 사용할 수 있어도 파일을 실제로 받는 데는 시간이 걸립니다. 그러므로 “재렌더링 생략”을 “다운로드 시간 0초”나 실측 속도 개선율로 바꾸지 않습니다.

같은 날 기록에는 캡처 배율 계산, 사용자 원본 이미지 주소를 저장 목록에 포함하는 처리, 앞면 마스크를 뒷면 설정으로 캡처하던 문제도 수정했다고 나옵니다. 이는 배치로 많이 처리하는 구조와 별도로, 만들어진 결과와 그 결과를 가리키는 정보가 맞아야 한다는 작업입니다. 당시 Phase 3의 흰 배경·스킵·URL 개수·다운로드 수동 확인은 대기로 남아 있습니다. 당시 수정과 시험 대기, §3·미해결 항목
