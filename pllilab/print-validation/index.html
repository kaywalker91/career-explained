고객의 디자인이 인쇄 파일이 되기까지

PLLI LAB은 고객이 꾸민 디자인을 실제 상품 제작에 사용할 수 있도록 연결하는 맞춤형 인쇄 플랫폼입니다. 고객이 사진·글자·스티커로 상품을 꾸미면, 제작 담당자와 디자이너는 그 디자인에 맞는 인쇄 이미지를 받아 다음 제작 작업을 진행해야 합니다. 화면에 디자인이 보이는 것만으로 인쇄 파일이 준비된 것은 아닙니다. 각 요소를 정해진 크기와 위치로 그려 파일로 저장하는 과정이 필요합니다. 이 이미지 생성 작업을 렌더링이라고 합니다. 서비스와 기술의 근거

이 프로젝트의 관리자 웹은 Flutter Web과 Dart로 만들었습니다. Flutter Web은 브라우저에서 화면을 구성하는 도구이고, CanvasKit·WebGL은 디자인을 그리는 데 사용하는 기술입니다. 만들어진 이미지 파일은 Storage에 보관하고, 어느 주문의 어느 이미지인지 가리키는 주소 등은 주문 정보를 보관하는 Firestore에 기록합니다. 따라서 고객 디자인 → 브라우저에서 이미지 생성 → 파일과 주소 저장 → 제작용 다운로드라는 흐름을 함께 봐야 합니다.

파일을 받았어도 고객의 디자인이 다 들어 있어야 했다

제작 담당자가 인쇄 파일을 받았는데 고객이 넣은 사진·스티커·글자가 빠져 있다면, 파일 다운로드가 끝났어도 제작에 그대로 쓰기 어렵습니다. 반대로 정상 이미지가 오류로 표시되면 불필요한 재처리와 확인이 이어집니다. 이 사건은 출력이 잘못된 경우와 검사가 잘못된 경우를 실물과 대조하고 각각 수정한 과정입니다. 사건 원본 · 요청 P03·P09

이 프로젝트에서 스티커는 캐릭터 장식뿐 아니라 배경 등 디자인에 얹는 요소를 포함하며 텍스트 스티커도 별도로 처리합니다. 디코딩은 PNG 등의 파일을 화면에 그릴 수 있는 이미지로 해석하는 일이고, 캡처는 요소를 배치한 결과를 한 장의 이미지로 만드는 일입니다. 파일을 미리 받기, 이미지로 해석하기, 실제로 그리기, 합성 결과를 저장하기는 서로 다른 단계입니다. 앞 단계의 성공만으로 최종 요소의 포함 여부를 확정할 수 없습니다.

준비가 끝나기 전에 찍는 문제와 잘못된 참조를 나누기

03-18에는 Image.memory로 표시 방식을 바꾼 기록이 있지만, 이후에도 누락이 이어졌습니다. 04-13 업무요약은 해당 방식에서 이미지 준비와 캡처의 시점이 어긋나 투명하게 찍히는 원인을 진단했습니다. 파일 바이트를 미리 읽었어도 그 바이트가 그릴 수 있는 이미지로 준비되기 전에 캡처하면 빠질 수 있다는 설명입니다. 따라서 이전 수정 기록의 제목을 근거로 전체 누락이 종결됐다고 보지 않습니다. 수정 경과 M01 · 04-13, §2

이때는 스티커를 사전 디코딩하고 준비된 이미지를 직접 표시하는 RawImage를 우선 사용하도록 했습니다. 가져온 파일을 표시 단계에서 다시 준비하게 맡기는 대신, 캡처 전에 이미지 준비를 마치는 방향입니다. 어떤 표시 경로가 선택됐는지와 스티커 집계도 로그·주문 정보에 남겼습니다. 이는 당시 진단·구현 기록이며, 모든 누락의 원인이 이 타이밍 하나였다는 뜻은 아닙니다.

05-12에는 별도로 배경 스티커의 인쇄용 URL 참조가 손상된 주문을 복구했습니다. URL 참조는 어느 이미지 파일을 읽을지 가리키는 주소입니다. 주소가 잘못됐다면 캡처를 늦춰도 필요한 원본을 가져오지 못하므로, 유효한 주소로 주문 데이터를 고친 뒤 다시 렌더링해야 했습니다. 03-17의 손상 URL 1,441건을 null로 정리한 기록 역시 잘못된 참조 정리이며 원본 이미지 복원 수가 아닙니다. 참조 정리·후속 복구 · 스티커 복구 표본

누락 판정을 보강하되 검사 결과도 실물에 맞춰 고치기

기존에는 일부 스티커가 빠져도 대체 처리인 폴백이 있었다는 표시만 남기고 저장하는 경로가 있었습니다. 누락 카운터가 호출되지 않아 문제를 세지 못하거나, 텍스트 스티커를 전체 개수에서 빼 분모가 줄어드는 결함도 기록됐습니다. 04-24에는 카운터와 분모를 보강하고 누락 비율이 10%를 넘는 경우 등을 **REJECT(결과 거부)**로 연결했습니다. 이 기준은 일부 누락을 거부하는 조건이며 모든 누락을 차단한다는 보장은 아닙니다. 04-24, §1

하지만 이 무렵의 픽셀 검사 결과에는 별개의 결함이 있었습니다. 04-27 기록에서 주문 사례 A 제품 [3]은 검사기에서 “예상 8개, 발견 6개, REJECT”였으나 사용자의 PNG 육안 확인으로는 8개 모두 정상이었습니다. 가까운 스티커를 한 덩어리로 세는 검사 방식 때문에 개수를 적게 잡은 오탐, 즉 실제로 정상인 것을 오류로 판정한 사례입니다. 출력물을 다시 고친 성공 사례로 세면 안 됩니다. 검사기 진단과 사용자 관찰 L04

후속에서는 스티커별 예상 위치 주변인 **ROI(관심 영역)**를 따로 검사했습니다. 9주문·116개 판정 중 115개 PASS와 실제로 빠졌는데 이전 검사에서 놓친 silent miss 1건을 분리한 기록입니다. 115/116은 해당 도구·표본의 판정이며 서비스 전체 인쇄 품질이나 누락 해결률이 아닙니다. 윤곽선 슬롯의 STRUCTURE_FAIL 34건은 당시 후속 조사로 남아 있었습니다. 04-24 기록의 픽셀 개수 예시도 04-27 오탐 정정을 함께 읽고 실물 결함 수로 일괄 확정하지 않습니다. 부분 누락 판정과 정정

데이터 복구 뒤 같은 제품의 출력을 비교하기

05-12 주문 사례 B의 제품 [4]에서는 배경 스티커 참조 4개를 유효한 URL로 고치고 다시 렌더링했습니다. 이후 주문 로그의 decodedImage=null은 16→0건, 403 응답은 4→0건으로 기록됐습니다. 이는 같은 주문 재렌더링 로그의 변화이며 제품 [4]만의 통계나 모든 제품의 최종 인쇄 품질 판정은 아닙니다. 동일 주문·제품 전후 · 복구 원문 L06

같은 주문의 제품 [7]에는 다른 문제가 있었습니다. 스티커의 기준 좌표만 보고 캔버스 밖이라고 판단해 3개를 지웠지만, 실제로는 회전·확대 뒤 인쇄 영역을 차지하는 요소였습니다. 사용자가 PNG 누락을 발견한 뒤 3개를 복원하고 다시 그렸습니다. 같은 제품의 전후 PNG를 비교해 영역이 채워진 기록이 있고, 제품 [4]는 같은 비교에서 변화가 없어 앞선 복구가 유지됐습니다. 좌표 한 쌍과 최종으로 그려지는 영역은 회전·배율 때문에 달라질 수 있다는 사례입니다. 도구의 정리 판정을 그대로 따르지 않고 사용자의 출력 확인을 바탕으로 잘못된 삭제를 되돌린 과정도 함께 남깁니다.

이날의 적용 범위는 출고 완료 6주문·결제 미완료 1주문의 데이터 복구입니다. 그중 추가 2주문에서는 앞·뒤 이미지와 각 마스크, 합계 8파일의 디코딩·알파 통계를 확인했습니다. 알파는 픽셀의 투명도를 나타내며 이미지가 전부 투명한지 등을 살필 때 쓰입니다. 8파일이 읽히고 이미지 영역이 있다는 확인과, 7주문의 모든 요소를 사람이 전수 검수했다는 주장은 다릅니다. 이 작업은 주문 데이터 적용·재렌더링이며 신규 웹 배포나 실제 재출고 완료로 바꾸지 않습니다. 재발 방어·정기 모니터링은 당시 후속입니다. 복구·표본·적용 범위

작은 정상 이미지를 빈 이미지로 버리던 기준 보정

06-08에는 텍스트 캡처 실패를 기록하는 코드가 웹에서 지원하지 않는 오류 보고 기능을 호출해, 주문 전체 처리가 끊기고 완료처럼 표시되던 결함을 수정했습니다. 같은 주문 사례 C의 제품 0~10에서 65파일 산출이 기록됐지만 제품 5의 마침표 빈캡처는 남았습니다. 06-08의 중단 복구와 06-09의 마침표 수정은 따로 봅니다. 같은 주문의 전후 · 프로젝트 메모 M-001

마침표는 정상으로 그려도 파일이 작을 수 있습니다. 그런데 기존에는 PNG가 2,048B보다 작으면 빈 이미지로 탈락시켰고, 정상 마침표 캡처는 1,156B였습니다. 파일 크기라는 간접 신호를 내용의 정상 여부와 동일하게 취급해 정상 결과를 버린 것입니다. 06-09에는 두 글자 이하는 256B, 긴 텍스트는 기존 2,048B 기준을 유지하도록 바꾸고, 캡처 경로의 미등록 글꼴을 NotoSans로 바꾸는 처리도 맞췄습니다. 06-09, §1
