이 글의 기준과 확인 범위

기존 기록과 2026-04-06~08·04-13·04-24·05-13·06-09 업무요약, 04-09 로그 분석·04-27·05-12 인계·06-08~09 프로젝트 메모의 해당 부분을 읽어 설명을 대조했습니다. 아래의 구현 내용은 당시 업무기록을 기준으로 하며, 후속 실행·배포 결과도 각 시점의 기록입니다. 이번 앱 실행·새 성능 측정·현재 운영 확인 결과와 구분합니다. 본인 확인과 당시 업무·분석·인계 기록을 바탕으로 작성했습니다. 내부 식별자는 사례명으로 바꿨으며, 비공개 근거는 제목으로 표시합니다.

공개 코드·기록은 링크로 연결하고, 비공개 근거 기록은 제목만 표시했습니다. 본인·AI·협업자의 기여, 확인된 결과와 남은 한계를 함께 읽어 주세요.

고객의 디자인이 인쇄 파일이 되기까지

PLLI LAB은 고객이 꾸민 디자인을 실제 상품 제작에 사용할 수 있도록 연결하는 맞춤형 인쇄 플랫폼입니다. 고객이 사진·글자·스티커로 상품을 꾸미면, 제작 담당자와 디자이너는 그 디자인에 맞는 인쇄 이미지를 받아 다음 제작 작업을 진행해야 합니다. 화면에 디자인이 보이는 것만으로 인쇄 파일이 준비된 것은 아닙니다. 각 요소를 정해진 크기와 위치로 그려 파일로 저장하는 과정이 필요합니다. 이 이미지 생성 작업을 렌더링이라고 합니다. 서비스와 기술의 근거

이 프로젝트의 관리자 웹은 Flutter Web과 Dart로 만들었습니다. Flutter Web은 브라우저에서 화면을 구성하는 도구이고, CanvasKit·WebGL은 디자인을 그리는 데 사용하는 기술입니다. 만들어진 이미지 파일은 Storage에 보관하고, 어느 주문의 어느 이미지인지 가리키는 주소 등은 주문 정보를 보관하는 Firestore에 기록합니다. 따라서 고객 디자인 → 브라우저에서 이미지 생성 → 파일과 주소 저장 → 제작용 다운로드라는 흐름을 함께 봐야 합니다.

사람이 시작하던 배치에 자동 시작 조건을 붙이기

앞의 배치 구조가 여러 주문을 처리할 수 있어도 관리자가 매번 실행 버튼을 눌러야 한다면, 언제 시작할지 사람이 챙겨야 합니다. 이 사건은 인쇄 이미지가 아직 만들어지지 않은 주문을 찾아 정해진 조건에서 처리 대기열을 시작하도록 바꾼 작업입니다. 4월 7일 업무요약에는 지정 관리자 계정으로 로그인할 때와 매일 21시에 실행하는 기능이 기록돼 있습니다. 모든 고객의 로그인으로 실행되는 기능은 아닙니다. 사건 원본 · 04-07 업무요약, §2

트리거는 처리를 시작하게 하는 계기입니다. 여기서는 로그인이나 정해진 시각이 그 계기이고, 큐는 처리를 기다리는 주문의 목록입니다. 스케줄러는 예약 시각에 실행을 요청하는 부분입니다. 이 시작 장치는 관리자 웹 화면에 구현된 것으로 기록돼 있습니다. 브라우저를 닫거나 PC가 절전 상태여도 별도 서버가 계속 실행한다는 보장으로 읽지 않습니다. 이 조건에서의 예약 실행은 추가 확인입니다.

자동화에 필요한 조건은 “버튼 없이 시작”보다 많았습니다. 여러 탭이 함께 시작해도 같은 주문을 중복 처리하지 않아야 하고, 결제하지 않은 주문은 제외해야 하며, 실패한 주문 하나 때문에 같은 시도를 끝없이 반복해서도 안 됐습니다. 시작 조건과 방어 처리, §2~4

실행 중이라는 표시는 주기적으로 살아 있어야 했다

localStorage는 같은 웹 출처의 탭들이 읽을 수 있는 브라우저 저장 공간입니다. 여기에 어느 탭이 자동 실행을 맡고 있는지 표시하는 **락(잠금)**을 두고, heartbeat로 30초마다 그 표시를 갱신하도록 했습니다. heartbeat는 담당 탭이 계속 동작 중임을 알리는 주기적인 갱신입니다. PLLI-001의 탭별 진행 보관과 달리, 여기서는 여러 탭이 실행 담당 정보를 공유하는 데 사용합니다. 같은 PC에서도 다른 브라우저 프로필, 다른 PC까지 조정하는 서버의 공통 잠금으로 확대하지 않습니다. 락·heartbeat 구현, §2

이 표시는 저장하기만 해서는 충분하지 않았습니다. 당시에는 탭 ID를 밀리초 단위로 만들고 저장할 때는 마이크로초 단위를 써서, 갱신하려는 탭과 잠금에 적힌 탭이 다르게 인식되는 결함이 있었습니다. 자신이 잡은 잠금인데도 갱신하지 못하면 유효 시간이 지나 다른 탭이 시작할 위험이 생깁니다. 탭 ID를 같은 값으로 통일하고 heartbeat 필드명도 맞췄습니다. 탭이 다시 보일 때의 갱신 보상도 기록돼 있습니다. 탭 ID·필드명 수정, §2~3

잠금을 얻지 못했을 때 계속 시도하는 반복문 역시 브라우저를 멈추게 할 수 있어 즉시 빠져나오도록 바꿨습니다. 이 변경의 이유는 “누군가 실행 중이면 기다리거나 종료할 수 있어야 한다”는 요구와 연결됩니다. 당시 기록에서 확인한 선택과 결함을 설명한 것이며, 다른 잠금 기술을 실제로 비교·기각했다고 덧붙이지 않습니다. 반복문 종료 수정, §4

시작부터 결과 저장까지, 다시 확인할 지점을 나누기

4월 7일의 자동 실행과 4월 8일의 후속 보완을 이어 보면 다음 흐름입니다. 이 표는 최종 코드를 실행해 추적한 결과가 아니라, 날짜별 구현 기록을 연결한 설명입니다.

단계 처리와 선택 이유
1. 시작 조건 확인 지정 관리자 로그인 또는 예약 시각에 자동 처리를 요청합니다. 계정 비교의 대소문자를 맞추고 주문 조회의 기준 날짜를 관리하도록 했습니다.
2. 실행 담당 조정 localStorage 잠금을 얻은 탭이 큐를 처리하고 heartbeat를 갱신합니다. 잠금을 얻지 못한 경로는 반복문에서 빠져나옵니다.
3. 대상 주문 선정 미렌더링 주문을 찾되 미결제 주문을 제외합니다. 대량 주문은 작은 묶음인 청크로 나눠 한 번에 다루는 범위를 줄이고, 실패 주문에는 재시도 횟수 상한을 둡니다. 당시 상한값·청크 크기를 임의의 숫자로 채우지 않습니다.
4. 실행 직전 재확인 04-08 보완에서는 큐에서 주문을 꺼낼 때 Firestore의 최신 상태를 다시 읽습니다. 큐에 넣은 뒤 다른 처리에서 이미 완성한 주문을 다시 그리는 일을 줄이려는 변경입니다.
5. 중단 뒤 재진입 메모리 한계 뒤 새로고침할 때는 로그인 정보 복원과 데이터 준비를 기다리고, 남은 잠금을 정리합니다. 수동 배치가 진행 중이면 자동 재개가 겹치지 않게 막는 조건도 추가했습니다.
6. 결과 확인 주문별 시작·완료·실패를 로그로 남기고 화면 상태를 갱신합니다. 렌더링·파일 업로드·주문 정보 저장 중 어느 단계에서 실패했는지 구분할 수 있도록 로그를 보강했습니다.

출처: 04-07, §2~5; 04-08, §1~4. 청크는 작업을 나누는 단위이며 동시에 여러 이미지를 그린다는 뜻은 아닙니다. 이미지 생성의 순차 처리 원리는 앞 사건과 함께 읽습니다.

특히 새로고침 직후에는 화면이 열렸어도 로그인 정보가 아직 복원되지 않을 수 있었습니다. 기다림 없이 주문을 처리하면 인증에 실패하고, 예전 잠금이 남아 있으면 재개가 막힐 수 있습니다. 따라서 “진행 목록을 남겼다”와 “다음 페이지에서 실행 준비가 됐다”는 별개 조건입니다. 로그 수집도 04-07 추가 기록 뒤 04-08 서비스 등록 누락을 수정한 기록이 있으므로, 코드 추가 날짜를 실제 로그 수집 확인 날짜로 바꾸지 않습니다.

청크·재시도 상한·세션의 유효 시간은 작업이 끝없이 이어지는 것을 제한하는 장치입니다. 그만큼 상한에 걸린 주문과 남은 작업의 확인이 필요하며, 실패를 모두 자동으로 고친다는 보장은 아닙니다. 주기적인 잠금 갱신과 중단 뒤 정리도 함께 관리해야 합니다.

자동 실행에서 본인이 맡은 범위

본인이 인계받은 렌더링 문제 해결 전반을 AI와 함께 직접 진행했고 주요 변경은 질의·승인을 받은 뒤 수행했다는 사용자 확인을 유지합니다. 04-07 업무요약의 본인 작업 사항에는 dev→prod 자동 렌더링 마이그레이션과 로그 수집 구현이 기재돼 있습니다. 이는 당시 본인의 작업 기록이며, 잠금 설계·각 코드 작성·수동 시험·배포 명령을 모두 혼자 수행했다는 확인은 아닙니다. 자동 실행의 세부 설계·검증·배포 분담은 추가 확인입니다. 역할 원본 · 04-07 본인 작업 사항, 문서 하단
