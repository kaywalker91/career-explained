고객의 디자인이 인쇄 파일이 되기까지

PLLI LAB은 고객이 꾸민 디자인을 실제 상품 제작에 사용할 수 있도록 연결하는 맞춤형 인쇄 플랫폼입니다. 고객이 사진·글자·스티커로 상품을 꾸미면, 제작 담당자와 디자이너는 그 디자인에 맞는 인쇄 이미지를 받아 다음 제작 작업을 진행해야 합니다. 화면에 디자인이 보이는 것만으로 인쇄 파일이 준비된 것은 아닙니다. 각 요소를 정해진 크기와 위치로 그려 파일로 저장하는 과정이 필요합니다. 이 이미지 생성 작업을 렌더링이라고 합니다. 서비스와 기술의 근거

관리자가 매번 시작하던 일을 로그인과 예약 시각에 연결했다

앞의 배치 처리는 여러 주문의 이미지를 차례로 만들 수 있게 했지만, 시작 버튼은 관리자가 눌러야 했습니다. 아직 인쇄 이미지가 없는 주문을 찾아 처리를 시작하는 일까지 사람이 챙겨야 했던 것입니다. 4월 7일에는 지정 관리자 계정으로 로그인할 때와 매일 21시에 미처리 주문을 찾아 자동으로 시작하도록 바꾼 내용이 기록돼 있습니다. 로그인이나 시각처럼 처리를 시작시키는 계기를 트리거라고 합니다. 모든 고객의 로그인으로 시작하는 기능은 아닙니다. 기존 흐름과 자동 시작, §2

저는 인계받은 렌더링 문제 해결 전반을 AI와 함께 직접 진행했고, 주요 변경은 사전에 질의하고 승인을 받아 수행했습니다. 이는 사용자 확인 내용이며, 4월 7일의 본인 작업 기록에도 개발용 프로젝트에서 운영용 프로젝트로 자동 렌더링 기능을 옮기고 로그 수집을 구현한 일이 적혀 있습니다. 다만 잠금 설계·각 코드 작성·수동 시험·배포를 모두 혼자 수행했다는 확인은 아닙니다. 사건별 세부 분담은 추가 확인이 필요합니다. 전체 역할의 확인 범위 · 04-07 본인 작업 사항, 문서 하단

이 자동 시작 장치는 관리자 웹 화면에 구현된 것으로 기록돼 있습니다. 브라우저를 닫거나 PC가 절전 상태여도 별도 서버가 계속 처리한다는 보장으로 읽지 않습니다. 그런 조건에서 예약 실행이 실제로 이어지는지는 추가 확인입니다.

처리할 주문을 고르고 반복 시도에 한계를 뒀다

시작 조건을 붙인 뒤에는 어떤 주문을 처리할지 정해야 했습니다. 아직 이미지를 만들지 않은 주문을 처리 대기 목록인 큐에 넣되, 결제하지 않은 주문은 제외했습니다. 주문 조회의 기준 날짜를 조절할 수 있게 하고, 관리자 계정의 대소문자 차이 때문에 시작 조건이 어긋나지 않도록 비교 방식도 맞췄습니다. 대상 선정과 시작 조건 보완, §4

대량 주문은 한 번에 다루는 범위를 작은 묶음으로 나눴습니다. 이 묶음을 청크라고 합니다. 여러 이미지를 동시에 그린다는 뜻은 아니며, 이미지를 만드는 순서는 앞 사건의 순차 처리를 따릅니다. 같은 주문이 계속 실패할 때도 재시도 횟수에 상한을 두고, 자동 처리 세션을 유효하게 볼 시간도 관리하도록 했습니다. 한 번의 실패 때문에 끝없이 같은 일을 반복하거나 긴 처리가 한없이 이어지지 않게 하는 장치입니다. 그만큼 상한에 걸린 주문과 남은 작업은 따로 확인해야 합니다. 당시 기록에 없는 청크 크기·재시도 횟수·유효 시간을 임의의 숫자로 채우지는 않습니다.

두 탭이 같은 일을 시작하지 않도록 담당 표시를 갱신했다

자동으로 시작할 수 있어도, 관리자가 같은 웹을 두 탭에서 열면 각 탭이 주문을 찾아 따로 실행할 수 있습니다. 그래서 어느 탭이 자동 처리를 맡고 있는지 표시하고, 다른 탭이 그 일을 함께 시작하지 않도록 했습니다. 이 실행 담당 표시가 잠금이며, 같은 웹 출처의 탭들이 읽을 수 있는 브라우저 저장 공간인 localStorage에 두었습니다. 한 탭의 새로고침 뒤 진행을 잇는 PLLI-001의 진행 보관과 달리, 여기서는 탭 사이에 실행 담당 정보를 공유합니다.

담당 표시가 남아 있다는 사실만으로 그 탭이 계속 일하고 있는지는 알 수 없습니다. 실행 중인 탭은 30초마다 표시를 갱신해 계속 동작 중임을 알리도록 했습니다. 이 주기적인 갱신이 heartbeat입니다. 탭이 다시 보일 때 갱신을 보완하는 처리도 기록돼 있습니다. 다만 이 방식의 범위는 같은 브라우저 프로필의 같은 웹 출처이며, 다른 PC나 브라우저 프로필까지 함께 조정하는 서버 잠금은 아닙니다. 잠금과 주기적 갱신, §2

이 갱신이 실패하는 결함도 고쳤습니다. 탭을 식별하는 번호를 만들 때와 잠금에 저장할 때 서로 다른 시간 단위를 사용해, 같은 탭인데도 다른 탭으로 인식하고 있었습니다. 그러면 자신의 담당 표시를 갱신하지 못해 유효 시간이 지나고 다른 탭이 시작할 위험이 생깁니다. 같은 탭 번호를 재사용하도록 바꾸고 갱신 필드명도 통일했습니다. 잠금을 얻지 못했는데 계속 반복하던 경로는 즉시 빠져나오도록 수정했습니다. 이 반복이 끝나지 않으면 브라우저가 응답하지 않을 수 있기 때문입니다. 탭 번호·갱신·반복문 수정, §3~4

새로고침 뒤에는 주문을 읽고 실행할 준비도 다시 갖춰야 했다

앞 사건처럼 메모리 한계에 닿으면 진행을 남기고 새로고침해 이어 처리하도록 했지만, 새 화면이 열렸다는 것만으로 주문을 읽을 준비까지 끝난 것은 아니었습니다. 4월 8일에는 로그인 정보가 복원되기 전에 처리를 시작해 인증에 실패하는 문제와, 이전 실행의 잠금이 남아 재개를 막는 문제를 보완했습니다. 로그인 복원과 데이터 준비를 기다리고 방치된 잠금을 정리하도록 했습니다. 수동 배치가 실행 중이면 자동 재개가 겹쳐 들어가지 않도록 막는 조건도 더했습니다. 재개 준비와 실행 충돌 보완, §2~4

대기 목록의 주문도 그대로 믿고 실행할 수는 없었습니다. 목록에 넣은 뒤 다른 처리에서 이미 이미지가 완성될 수 있기 때문입니다. 주문을 꺼낼 때 주문 정보를 보관하는 Firestore에서 최신 상태를 다시 읽고, 이미 처리된 주문은 건너뛰도록 했습니다. 진행을 이어 가면서 같은 주문을 불필요하게 다시 그리지 않기 위한 변경입니다.

관리자가 진행 상황을 확인하고 나중에 실패 지점을 찾을 수 있도록, 화면에는 미처리·진행 중·완료·실패 상태를 표시하고 주문별 시작·완료·실패를 로그로 남겼습니다. 이미지 생성·파일 업로드·주문 정보 저장 중 어느 단계에서 실패했는지도 구분하도록 보강했습니다. 다만 로그 기능을 추가한 기록 뒤에 4월 8일의 서비스 등록 누락 수정이 이어지므로, 코드 추가 날짜만으로 실제 로그 수집까지 확인됐다고 쓰지는 않습니다. 화면과 로그 추가, §5 · 로그 서비스 보완, §1
