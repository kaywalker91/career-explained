글자 대비는 색 이름보다 실제 배경과의 조합을 봐야 한다

심사 화면에서 주황색 재난문자 제목과 폭염 표시는 대비 측정값이 각각 2.7:1·2.6:1이었고, 최소 3:1 이상으로 수정하라는 요구를 받았습니다. 명도 대비는 글자·아이콘과 배경이 밝기에서 얼마나 구별되는지를 나타냅니다. 같은 글자색도 어느 배경 위에 놓느냐에 따라 값이 달라지므로 두 색을 한 쌍으로 살펴야 합니다. 이 지적은 Android PDF 17쪽·iOS PDF 19쪽에서 확인했습니다. Android 지적 위치 · iOS 지적 위치

보관 코드에서는 여러 화면이 함께 쓰는 연한 글자색이 더 진해진 것을 확인할 수 있습니다. 2025-08-04의 재직 중 보관본에는 #999999, 2026-01-11의 후속 보관본에는 #757575가 정의돼 있습니다. 이처럼 공통 색상을 한곳에서 정하면 그 값을 참조하는 화면에 같은 색을 적용할 수 있습니다. 화면마다 따로 지정한 색은 별도로 살펴야 하며, 같은 값을 쓰더라도 배경·그라데이션·투명도가 다르면 대비를 다시 확인해야 합니다. 이전 색상 · 후속 색상

진해진 정도는 계산으로도 살펴볼 수 있습니다. 코드의 ContrastChecker는 색의 빨강·초록·파랑 성분에서 밝기를 구하고, 밝은 쪽과 어두운 쪽을 비교해 대비 비율을 계산합니다. 불투명한 회색 글자를 흰 배경 #FFFFFF에 놓는 조건으로 이 식을 적용하면 #999999는 약 2.85:1, #757575는 약 4.61:1입니다. 이 계산은 해당 회색 조합이 더 구별되게 바뀌었음을 설명합니다. 앞서 심사에서 지적받은 주황색 제목·폭염 표시와는 다른 조합이므로 그 지적까지 해소됐다는 증거로 쓸 수는 없습니다. 대비 계산식

그림의 뜻과 지금 가능한 동작을 화면 읽기 도구에 전달한다

색을 구별할 수 있게 바꾸어도 음성 안내로 앱을 쓰는 사용자는 화살표가 어느 목록을 움직이는지 알아야 합니다. 행동요령 목록의 왼쪽 화살표라면 ‘이전 행동요령 카테고리로 이동한다’는 목적과 지금 이동할 수 있는지를 함께 전달해야 합니다. Flutter의 Semantics는 이런 설명과 상태를 화면 읽기 도구에 전달할 정보를 붙이는 구성입니다.

코드는 현재 목록 위치에 따라 설명과 동작을 함께 고릅니다. 이전 항목이 있으면 label에 이동 목적을 담고, hint에 두 번 탭하라는 조작 안내를 붙이며, enabled로 사용 가능 상태를 전달합니다. 실제 화살표의 누르기 동작도 이전 페이지 이동에 연결돼 있습니다. 첫 항목에서는 설명이 ‘첫 번째 행동요령 카테고리’로 바뀌고 사용 불가 상태와 함께 누르기 동작도 꺼집니다. 오른쪽 화살표는 마지막 항목인지에 따라 같은 방식으로 달라집니다. 개별 행동요령 항목에도 제목에 따른 설명과 조작 안내가 붙어 있습니다. 화살표의 목적·상태 · 행동요령 항목의 설명

여기까지 확인한 것은 설명·상태·일반 누르기 동작을 정한 코드입니다. 바깥에서 설명을 붙이는 동시에 ExcludeSemantics로 안쪽 그림·글자의 의미 정보를 제외하고, 행동요령 요소에는 button: false를 지정합니다. 중복 안내를 조정할 수 있는 구성이지만 실제 화면 읽기 도구가 버튼으로 인식하고 활성화할 수 있는지까지 코드에 설명이 있다는 이유로 판정할 수는 없습니다. 두 운영체제에서 실제 낭독·초점 이동·활성화를 확인하는 일은 남아 있습니다.

페이지를 고른 뒤 현재 위치와 안내도 함께 바뀌어야 한다

행동요령의 이동 목적을 설명했다면, 재난 문자를 넘길 때에는 이동한 뒤 어디에 있는지도 알려야 합니다. 문자가 세 개일 때 두 번째 문자를 읽고 있다면 현재 위치와 전체 수가 함께 필요합니다. 화면 아래의 페이지 표시기가 다른 항목을 가리키거나 음성 안내가 이전 위치에 머물면 사용자는 지금 읽는 내용을 파악하기 어렵습니다. 다음은 보관 코드가 이 정보들을 어떻게 연결하는지 보여 주는 예입니다.

페이지 표시기는 각 항목을 ‘현재 페이지’와 ‘페이지 선택’으로 구별하고, 전체에는 ‘현재 몇 번째, 총 몇 개’라는 안내 정보를 붙입니다. 재난 문자 화면이 실제 목록 수와 현재 위치 번호를 표시기에 전달하므로 이 값으로 설명을 만들 수 있습니다. 내부 위치 번호인 인덱스는 0부터 세지만 사용자에게 보여 주는 번호에는 1을 더합니다. 그래서 두 번째 문자는 내부에서 1로 다루면서 안내는 ‘2번째’로 만들 수 있습니다.

다른 항목을 고르면 표시기는 선택한 번호를 화면에 전달하고, 화면은 그 페이지로 이동을 요청합니다. 이어 페이지 변경이 발생하면 현재 인덱스를 저장하고 재난 문자 변경 안내 함수를 호출합니다. 저장한 위치는 다시 표시기에 전달돼 현재 항목 설명을 갱신하는 데 쓰입니다. 이처럼 이동 요청 → 변경된 위치 저장 → 표시·안내 갱신을 연결한 것이 확인된 처리 흐름입니다. 개별 항목과 전체 수의 의미 정보 · 표시기 전체 안내 · 재난 문자 화면 연결

다음 도식은 이 코드의 호출 연결입니다. 실제 TalkBack·VoiceOver에서 이동과 낭독이 성공했다는 실행 결과를 그린 것은 아닙니다.

시험은 무엇을 확인하도록 작성됐는지까지 구분한다

다른 작업에서 공통 색상이나 표시기 코드를 바꾸면 같은 문제가 다시 생길 수 있습니다. 저장소의 자동 시험은 어떤 조건을 다시 확인할지 코드로 남깁니다. 색상 시험은 대표 글자색과 흰 배경을 한 쌍씩 계산해 4.5:1 이상인지 확인하도록 작성돼 있습니다. 지정한 아이콘·테두리 등의 일부 조합에는 3:1 이상을 기대합니다. 앞서 본 심사 화면의 최소 3:1 요구와 이 시험의 대상·기준을 구분해야 합니다. 시험 이름에 ‘모든 색상’이나 ‘모든 UI’라는 말이 있어도 실제 검사 범위는 코드에 나열된 조합입니다. 색상 시험의 대상과 기대값

페이지 표시기 시험은 앞서 설명한 세 개 중 두 번째 항목을 현재 항목으로 설정해 ‘현재 2번째, 총 3개’라는 안내 정보를 확인하도록 작성돼 있습니다. 현재 항목과 선택 가능한 항목의 설명을 구별하는 경우, 두 번째 항목을 누르면 인덱스 1이 전달되는지 확인하는 경우도 있습니다. 이는 Flutter의 화면 구성 단위인 위젯에 값을 넣어 설명과 선택 처리를 검사하는 정의입니다. 전체 앱에서 재난 문자를 읽고 넘기는 사용 과정은 휴대폰의 화면 읽기 도구로 별도 확인해야 합니다. 이번에는 이 시험들을 실행하지 않았으며 통과했다고 보고하지 않습니다. 페이지 안내·선택 시험 정의

여러 화면이 함께 쓰는 색상·화살표·표시기에 같은 정보를 담고 자동 시험으로 일부 조건을 남긴 이유는 코드 구조에서 읽은 해석입니다. 당시 제가 정한 우선순위·실제로 비교한 대안·AI 공동 작성 여부와 개별 분석·수정·시험·배포 분담은 추가 확인으로 남깁니다. 사용자는 개인 기여·후속 재심사 자료를 나중에 제공하겠다고 답했습니다. 두 앱의 Flutter 전환을 단독 수행했다는 확인을 이 세부 작업 전체의 단독 수행으로 확대하지 않습니다. 사용자 후속 답변과 적용 범위
