글자 대비는 색 이름보다 실제 배경과의 조합을 봐야 한다

명도 대비는 앞에 놓인 글자·아이콘과 뒤의 배경이 밝기에서 얼마나 구별되는지를 말합니다. Android PDF 17쪽·iOS PDF 19쪽의 메인 화면 지적에는 재난문자 제목과 폭염 표시가 표시돼 있고, 대비 측정값 2.7:1·2.6:1, 최소 3:1 이상으로 수정하라는 요구가 있습니다. 이 숫자는 해당 심사 화면의 측정값입니다. Android 지적 위치 · iOS 지적 위치

보관된 코드에서 관찰한 변화 중 하나는 여러 화면이 공유하는 연한 글자색입니다. 2025-08-04의 재직 중 보관본에는 #999999, 2026-01-11의 후속 보관본에는 더 진한 #757575가 정의돼 있습니다. 공통 색상으로 관리하면 이 값을 참조하는 화면들이 같은 값을 사용하게 할 수 있습니다. 반면 직접 지정한 색상·다른 배경·그라데이션·투명도까지 한 번에 확인되는 것은 아닙니다. 이전 색상 · 후속 색상

코드의 ContrastChecker는 두 색의 RGB 값에서 밝기를 계산하고, 더 밝은 쪽과 어두운 쪽을 비교해 대비 비율을 구합니다. 이번 문서 작성에서 불투명한 두 회색을 흰 배경 #FFFFFF에 놓는 조건으로 같은 계산식을 적용하면 #999999는 약 2.85:1, #757575는 약 4.61:1입니다. 이는 색상 쌍의 계산 결과입니다. 심사서의 주황색 재난문자 제목·폭염 표시와는 다른 조합이므로 해당 지적이 모두 해소됐다는 증거로 쓰지 않습니다. 대비 계산식

그림의 뜻과 지금 가능한 동작을 화면 읽기 도구에 전달한다

화살표 그림이 보여도 음성 안내만 듣는 사람은 그것이 어느 목록을 움직이는지 알기 어렵습니다. Flutter의 **Semantics**는 화면 요소의 목적·상태·조작 안내를 보조기술에 전달하는 정보를 붙이는 구성입니다. 여기서 label은 무엇인지 설명하고, hint는 어떻게 조작하는지 보충하며, enabled는 사용할 수 있는 상태를 나타냅니다.

행동요령 카테고리의 이전·다음 화살표는 이동할 수 있을 때 이동 목적과 두 번 탭 안내를 제공합니다. 첫 항목이나 마지막 항목에서는 그 위치를 설명하고 사용 가능 상태를 바꿉니다. 개별 행동요령 항목에도 제목에 따른 설명과 조작 안내가 연결돼 있습니다. 목적을 코드에 담는 과정을 확인한 것이며 실제 낭독 결과와 구분합니다. 화살표의 목적·상태 · 행동요령 항목의 설명

이 코드에는 자식 요소의 의미 정보를 제외하는 **ExcludeSemantics**도 있습니다. 안쪽 그림·글자가 중복 안내되는 것을 조정할 수 있지만 필요한 역할·동작까지 실제로 전달되는지 확인해야 합니다. 특히 이 행동요령 래퍼는 button: false를 사용합니다. 설명 문구가 존재한다는 사실만으로 버튼 역할·보조기술의 활성화 동작까지 정상이라고 판정하지 않습니다. 두 운영체제에서 실제 읽기·초점 이동·활성화를 확인하는 일은 남아 있습니다.

페이지를 고른 뒤 현재 위치와 안내도 함께 바뀌어야 한다

재난 문자가 여러 장이면 사용자는 현재 읽는 항목과 전체 수를 알아야 합니다. 초점은 화면 읽기 도구나 키보드가 지금 안내·조작하는 대상을 뜻합니다. 눈에 보이는 선택 표시와 화면 읽기 도구의 안내가 같은 위치를 가리키는지도 중요합니다.

현재 페이지 표시기 코드는 각 항목에 “현재 페이지” 또는 “페이지 선택”이라는 설명을 구분하고, 표시기 전체에는 현재 몇 번째인지와 총 몇 개인지를 전달합니다. 재난 문자 화면은 이 표시기에 실제 목록 수·현재 인덱스를 넣습니다. 항목을 선택하면 해당 페이지로 이동을 요청하고, 페이지 변경이 발생하면 현재 인덱스를 저장한 뒤 재난 문자 안내 함수를 호출합니다. 개별 항목과 전체 수의 의미 정보 · 표시기 전체 안내 · 재난 문자 화면 연결

다음 도식은 이 코드의 호출 연결입니다. 실제 TalkBack·VoiceOver에서 이동과 낭독이 성공했다는 실행 결과를 그린 것은 아닙니다.

시험은 무엇을 확인하도록 작성됐는지까지 구분한다

색상 대비 시험은 대표 글자색과 흰 배경의 조합에 4.5:1 이상, 지정한 아이콘·테두리 등 일부 조합에는 3:1 이상을 기대하도록 작성돼 있습니다. 심사서의 최소 3:1 요구와 코드의 조합별 시험 조건을 같은 범위의 판정으로 합치지 않습니다. 시험 이름에 모든 색상·UI가 들어가더라도 실제 검사 대상은 코드에 나열된 조합입니다. 색상 시험의 대상과 기대값

페이지 표시기 시험에는 3개 중 두 번째 항목을 현재 항목으로 두고 안내 문구를 확인하는 경우, 현재 항목과 선택할 항목의 라벨을 구별하는 경우, 두 번째 항목 선택이 인덱스 1을 전달하는지 확인하는 경우가 정의돼 있습니다. 이는 Flutter 위젯이라는 화면 구성 단위의 자동 검사 정의입니다. 실제 휴대폰의 화면 읽기 도구로 순서대로 탐색하고 내용을 이해하는 것까지 대신하지는 않습니다. 이번에는 이 시험들을 실행하지 않았으며 통과했다고 보고하지 않습니다. 페이지 안내·선택 시험 정의

접근성 대응은 기존 이력서에 기재된 개인 경험입니다. 두 Flutter 앱 전환을 단독 수행했다는 사용자 확인은 유지하되, 그것만으로 개별 접근성 분석·코드 수정·시험·실기기 확인·배포까지 모두 혼자 수행했다고 넓히지 않습니다. 사용자는 이 사건의 개인 기여·후속 재심사 자료를 나중에 제공하겠다고 답했습니다. 당시 판단·대안 비교·AI 공동 작성 여부와 세부 분담은 추가 확인으로 남깁니다. 사용자 후속 답변과 적용 범위

여러 화면에서 반복되는 색상·화살표·페이지 표시기를 공통 요소로 보완하면 같은 정보를 일관되게 전달할 수 있다는 것은 코드 구조에서 읽은 선택 이유입니다. 실제로 본인이 어떤 순서로 우선순위를 정했는지와 구분합니다. 저장소의 접근성 수정 문서도 제목과 본문이 수정 계획이므로 실제 완료·재심사 성공 보고서로 사용하지 않습니다. 계획 문서의 성격과 해석

확인된 결과는 심사에서 드러난 사용 문제를 공통 색상 변경·행동요령의 설명·재난 문자 페이지 안내·관련 시험 정의와 연결할 수 있다는 것입니다. 이번에는 두 PDF의 해당 쪽을 텍스트·이미지로 다시 대조하고 고정 코드와 시험 정의를 읽었습니다. 2025년 심사·재직 중 색상과 2026년 보관 코드의 차이를 보존하며, 코드가 Git에 보관된 날짜를 실제 수정·배포일로 바꾸지 않습니다.
