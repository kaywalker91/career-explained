전환 중 문제는 데이터를 받은 뒤 화면을 맞추는 일이었다

안전디딤돌에서 내 지역의 날씨를 보려면 앱이 위치를 확인하고 날씨 정보를 받아야 합니다. 두 작업이 끝날 때까지는 시간이 걸립니다. 그동안 무엇을 보여 주고, 결과가 도착하면 어느 화면을 바꿀지까지 정해야 사용자가 지금 보는 정보를 이해할 수 있습니다. 이 장면은 데이터 갱신 문제를 설명하기 위한 예입니다. 당시 지역명과 날씨가 어긋난 특정 장애를 재현한 기록은 아닙니다.

저는 안전디딤돌·이머전시레디 두 앱의 Flutter 앱 부분 전환을 단독 수행했습니다. 이 범위는 사용자 확인 사항입니다. 기존 이력서에는 Android·iOS용으로 따로 만든 앱을 공통 코드로 옮기던 중 기존 데이터를 맞춰 갱신하는 문제가 자주 생겼고, 사용자 경험과 서비스 안정성을 우선해 데이터 흐름을 단순화했다고 적었습니다. 전환을 담당한 사실과 당시 문제·대응에 관한 본인의 기록을 구분해 읽어야 합니다. 역할의 사용자 확인 · 원문에서 확인한 문제·대응·결과

Flutter는 Dart라는 언어로 Android·iOS의 화면과 동작을 공통 코드에서 개발하는 도구입니다. 같은 기능을 두 플랫폼에서 함께 관리할 수 있지만, 위치나 날씨가 바뀔 때 화면을 갱신하는 일은 따로 연결해야 합니다. 운영체제별 위치 권한과 실제 기기에서의 동작도 확인해야 하므로 공통 코드 전환만으로 모든 처리가 같아지는 것은 아닙니다.

공통 화면·상태 관리·데이터 조회에 각각 역할을 줬다

이력서에 적은 대응은 화면에 반영할 정보를 Riverpod으로 관리하고, 데이터를 가져오는 일은 Repository라는 창구로 모으는 것이었습니다. 위치와 서버 응답을 기다리는 동안 화면 전체를 멈추지 않고 다른 일을 할 수 있게 하는 방식을 비동기 처리라고 합니다. 요청과 응답 사이에 시간이 생기기 때문에 데이터 값과 함께 “조회 중인지”, “저장된 정보가 있는지”, “실패했는지”도 관리해야 합니다. 이런 화면 판단의 재료를 상태라고 부릅니다. 전후 흐름과 기여의 근거

Riverpod은 화면이 필요한 상태를 구독하도록 연결하는 도구입니다. 구독은 정보가 바뀌면 화면이 그 변화를 받아 다시 그릴 수 있게 연결해 둔다는 뜻입니다. Provider는 이 연결을 제공하는 단위이며, 여기서는 상태를 바꾸는 담당 객체도 함께 둡니다. 화면마다 조회 결과를 따로 전달하기보다, 필요한 화면이 정해진 상태를 읽도록 흐름을 정리하는 방법입니다.

Repository는 “이 위치의 날씨를 가져와 달라”처럼 데이터를 요청하는 창구입니다. 서버에 물을지, 기기에 저장한 정보를 쓸지 고르는 처리를 화면 밖에 모읍니다. 그러면 화면은 받은 상태를 어떻게 보여 줄지, 조회 담당은 어디에서 정보를 가져올지 각각 다룰 수 있습니다. 대신 어떤 상태를 어느 화면이 구독하는지, 저장본은 언제 갱신할지 연결 규칙을 관리해야 합니다. 이 설명은 구조의 역할과 비용을 풀어 쓴 것이며, 당시 본인이 여러 대안을 비교·측정했다는 뜻은 아닙니다.

이력서의 단방향 흐름은 이 글에서 조회 요청 → 상태 변경 → 구독한 화면의 갱신이라는 순서를 뜻합니다. 앱 전체의 상태가 하나뿐이라거나 서버와 기기의 모든 정보가 항상 일치한다는 보장은 아닙니다. 아래에서는 이 방법이 코드에 어떻게 나타나는지 두 시점으로 나누어 봅니다.

재직 중 코드에서는 위치 상태와 날씨 화면의 구독이 연결돼 있다

재직 기간에 포함되는 2025-08-04의 재직 중 보관본에서는 현재 위치와 이전에 저장한 위치를 따로 보관합니다. 조회 중인지, 오류가 생겼는지, 갱신이 진행 중인지도 함께 둡니다. 사용할 위치를 고를 때는 현재 위치를 먼저 보고, 그것이 없으면 저장된 위치를 선택합니다. 캐시는 이렇게 다시 쓰기 위해 보관한 정보입니다. 저장 위치를 쓸 수 있다는 것과 지금 새로 위치를 확인했다는 것은 구분해야 합니다. 위치 상태와 선택 규칙

같은 위치 조회를 여러 곳에서 요청할 때도 처리 순서가 필요합니다. 이 보관본은 강제 갱신이 아닌 요청에서 이미 진행 중인 위치 조회가 있으면 그 결과를 함께 기다립니다. 이미 하는 일을 다시 시작하지 않고 재사용하는 경로입니다. 강제 갱신에는 이 조건을 적용하지 않으므로 모든 중복 요청을 막는다고 설명할 수는 없습니다. 진행 중인 조회 재사용

날씨 화면은 위치·위치 권한·날씨 캐시 상태를 구독합니다. 코드의 ref.watch가 그 연결입니다. 사용할 위치가 있으면 주소를 표시하고, 위치가 없으면서 조회 중이거나 첫 조회 중이면 “위치 확인 중...”을 보여 줍니다. 둘 다 해당하지 않으면 서울특별시 중구를 기본 지역으로 사용합니다. 날씨 데이터와 조회 중 여부는 날씨 캐시 상태에서 읽습니다. 같은 화면에서도 위치와 날씨의 준비 여부를 각각 살펴 표시를 고르는 구조입니다. 재직 중 화면의 상태 구독과 분기

여기까지 코드에서 확인한 것은 상태에 따라 화면의 표시를 고르는 연결입니다. 저장 위치나 기본 지역이 보인다고 새 GPS 조회가 성공한 것은 아닙니다. 저장 정보가 얼마나 최신인지, 권한별 화면과 위치·날씨의 모든 조합이 정상인지에는 별도의 실행 확인이 필요합니다.

후속 보관 코드에서는 조회 담당과 상태 변경 순서가 더 구체적으로 보인다

퇴사 뒤인 2026-01-11의 후속 보관본에서는 날씨 조회의 역할 분리를 더 구체적으로 읽을 수 있습니다. 날씨 Provider는 Repository에 주소·위도·경도를 전달해 조회를 요청합니다. 이 작업을 감싼 공통 처리 함수인 executeAsync가 조회 중 상태를 먼저 설정한 뒤 작업의 결과를 기다립니다. 조회가 실패했거나 데이터가 없으면 예외로 처리하고, 데이터를 받으면 성공 상태에 담습니다. 예외가 발생하면 공통 처리가 오류 상태로 바꿉니다. 화면이 읽을 상태를 작업의 시작과 결과에 맞춰 바꾸는 순서입니다. 날씨 조회의 역할 분리 · 공통 상태 처리

다음 그림은 이 후속 보관본의 두 함수가 조회와 상태 변경을 연결하는 순서입니다. 앞의 2025년 날씨 화면과 합쳐 한 시점의 전체 실행을 관찰한 그림으로 읽지 않습니다.

데이터를 어디서 가져올지 고르는 예는 같은 후속 보관본의 재난 문자 Repository에서 볼 수 있습니다. 일반 조회는 저장본을 먼저 읽고, 비어 있지 않으면 그대로 반환합니다. 저장본이 없거나 비어 있을 때, 또는 강제 갱신을 요청했을 때 서버에서 받아 저장한 뒤 반환합니다. 서버 조회나 응답 저장 중 예외가 나면 마지막 저장본을 다시 읽으려 하고, 저장본도 없으면 오류를 전달합니다. 강제 갱신도 실패 뒤에는 저장본을 시도하므로, 강제 갱신 요청 자체가 새 정보 확보의 증거는 아닙니다. 저장본·서버 선택과 실패 처리
