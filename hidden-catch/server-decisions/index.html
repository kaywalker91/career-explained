카드로 접속한 사용자의 한 판이 관리자 기록이 되기까지

이 서비스는 원본과 바뀐 그림을 보고 다른 부분을 찾는 웹 게임입니다. 이용자는 NFC 카드를 휴대폰에 가까이 대 게임으로 들어가고, 로그인한 뒤 판을 선택해 플레이합니다. NFC는 가까이 댄 카드의 정보를 읽는 통신 방식입니다. 이 프로젝트에서는 카드 발급·접속과 플레이할 수 있는 횟수를 연결하는 데 쓰였습니다. 도전권은 한 판을 시작할 수 있는 기회이고, 포인트는 플레이 결과에 따라 받는 보상입니다. 서비스·역할 근거

휴대폰 브라우저는 그림을 보여 주고 터치를 받는 클라이언트입니다. 서버는 로그인한 사람이 누구인지, 그 사람이 해당 판을 할 수 있는지, 횟수와 포인트를 어떻게 반영할지 판단합니다. 관리자는 웹 화면에서 그림을 발행하고 상품·카드를 관리하며 플레이 기록을 확인합니다. 따라서 관리자 발행 → 휴대폰의 그림 수신 → 판 시작·플레이 → 서버 정산 → 관리자 기록의 흐름을 함께 봐야 합니다. 서버·관리자 기능에는 JavaScript와 Node.js를 사용하고, 데이터 보관에는 Firestore와 파일 저장소를 사용하는 경로가 있습니다.

기기를 바꿔도 이어지는 게임, 발급할 때 정한 횟수를 지키는 카드

이 게임의 도전 횟수는 실물 NFC 카드와 연결돼 있었습니다. 이용자는 카드를 연결해 얻은 횟수로 게임을 하고, 결과에 따라 포인트를 받았습니다. 그런데 로그인하면서 남은 도전 횟수가 사라지는 문제가 기록돼 있었습니다. 별점과 다음 판을 열 수 있는지도 휴대폰 안에만 저장해, 기기를 바꾸거나 브라우저의 저장 정보를 지우면 진행 상황을 잃을 수 있었습니다. 점수·포인트는 브라우저가 계산한 값을 서버에 보내던 상태였습니다. 이용자의 계정·진행도·보상을 서버에서 일관되게 다룰 필요가 있었습니다. 당시 문제와 요구사항

저는 서버·관리자 웹을 중심으로 담당했습니다. 이 범위는 사용자 확인으로 확정돼 있습니다. 아래에서는 그 담당 업무 중 로그인·보상 계산·카드 발급을 설명합니다. 협업자가 만든 회원·인증 기능과 화면 변경, AI의 통합·구현·시험·배포·휴대폰 조작 기록이 함께 있으므로, 개별 코드 작성과 검증을 모두 제가 단독으로 했다고 설명하지는 않습니다. 제 승인 시안이 코드에 참조된 점과 오류 제보·보완 지시는 해당 장면에서 구분합니다. 담당 범위와 협업 근거

이용자를 확인한 뒤, 그 사람의 판을 서버에서 계산하기

계정에 진행도와 보상을 남기려면 먼저 요청한 사람이 누구인지 확인해야 합니다. 이것이 인증입니다. 카카오 로그인에서는 서버가 카카오와 직접 통신해 로그인 과정에서 받은 인증 코드를 교환하고 이용자 정보를 조회하도록 했습니다. 그 결과를 Firebase라는 인증 서비스의 계정 자격으로 연결했습니다. 브라우저가 보낸 사용자 정보만으로 계정을 정하지 않고, 로그인 제공자의 확인을 거치는 흐름입니다. 당시 8월 11~12일 일지에는 네이버 로그인부터 회원 생성·게임 데이터 조회, 개발용 서버 분리·배포와 미로그인 관리자 접근 차단이, 8월 18일 일지에는 실제 기기의 카카오 로그인·재로그인 확인이 보고돼 있습니다. 로그인 변경과 당시 결과

누구인지 확인한 다음에는 그 사람이 플레이한 판인지, 어떤 결과를 받을지 판단해야 합니다. 서버가 요청자의 판인지 확인하고, 서버 시계·그 판의 정답 위치·클릭 기록을 바탕으로 승패·별점·포인트를 계산하는 구조로 옮겼습니다. 결과를 계정의 보상과 기록에 반영하는 처리가 정산입니다. 브라우저가 계산한 최종 숫자를 받아들이던 방식에서, 서버가 계산에 필요한 기록을 받아 같은 규칙을 적용하는 방식으로 바꾼 것입니다.

이때 별점·포인트를 주는 기존 규칙은 유지했습니다. 계산 장소를 옮기면서 이용자가 받는 보상까지 달라지지 않도록 한 변경입니다. 별점과 다음 스테이지의 해금 정보도 서버에서 조회하고, 다음 판을 열 조건을 서버가 확인하도록 바꾼 기록이 있습니다. 기기 안의 저장 정보에만 의존하던 진행도 관리를 계정 기준으로 옮긴 과정입니다. 이 구조를 확인한 것만으로 모든 부정 사용이나 저장 실패가 차단됐다고 판단하지는 않습니다. 서버 계산·진행도 변경

상품을 골라 발급하되, 이미 준 카드의 횟수는 보존하기

관리자에게는 카드마다 상품 코드와 도전 횟수를 입력하는 일이 있었습니다. 상품별 기본 횟수를 미리 등록하고 발급 화면에서 상품을 고르면 그 횟수가 표시되도록 바꿨습니다. 사용할 상품이 없으면 발급 버튼을 잠그도록 했습니다. 9월 23일 화면 코드에는 제가 승인한 시안을 참조했다는 기록이 있습니다. 당시 일지는 상품의 엑셀 대량 등록과 상품 선택 발급, 게임 화면의 상품명·카드 잔여 횟수 표시까지 보고합니다. 이는 입력 절차가 달라졌다는 근거이며, 오발급이 0건이 됐거나 일정 비율로 줄었다는 측정은 아닙니다. 상품 관리와 본인 승인 기록 · 당시 상품 운영 결과

상품을 골랐다고 화면의 숫자를 그대로 발급에 쓰지는 않았습니다. 서버가 상품 목록에서 기본 횟수를 읽어 카드에 복사했습니다. 그 사이 상품 설정이 바뀌어 화면에서 본 횟수와 서버의 현재 횟수가 다르면 발급을 중단했습니다. 관리자가 확인한 조건과 다른 조건으로 카드가 나오는 일을 막기 위한 처리입니다. 다만 이 비교가 모든 동시 변경을 한꺼번에 차단한다는 보장은 아닙니다. 발급 시 서버 확인

발급한 뒤에는 상품의 현재 기본값과 그 카드에 부여한 값을 나눠야 했습니다. 상품 설정은 다음에 발급할 카드의 기준입니다. 기존 카드를 다시 저장했다는 이유로 새 기본값을 복사하면, 이미 부여한 횟수까지 달라질 수 있습니다. 후속 수정에서는 같은 상품을 다시 보낸 경우 상품 변경 처리를 건너뛰어 카드의 횟수를 덮어쓰지 않도록 했습니다. 발급 당시 값을 카드에 따로 두고, 이후 상품 수정·비활성화와 구분해 보존하는 방식입니다. 그만큼 상품 목록과 카드 값을 나눠 관리하고 설정이 바뀐 상황도 안내해야 합니다. 기존 카드 보존 변경

카드 접속에 쓰는 코드도 보강했습니다. 기존 코드는 발급 시각을 바탕으로 만들어 일부를 추측할 수 있었습니다. 이를 암호학적 난수, 즉 예측하기 어렵게 생성한 무작위 값으로 바꾸되, 카드에 기록할 주소 길이와 관리자 화면의 표시 폭은 유지하도록 코드 형식은 보존했습니다. 8월 18일에는 기존 태그를 폐기·재발급하고 실물 카드로 확인했다는 보고가 있습니다. 해당 코드 생성 방식과 카드의 확인 결과이며 전체 접근 경로의 보안을 입증한 것은 아닙니다. 난수 변경과 실물 확인

방금 로그인했는데 만료됐다고 판단하던 조건 고치기

10월에는 로그인 유지 조건에서도 문제가 확인됐습니다. 로그인 시각은 인증 서비스의 시계로 찍히는데, 서버는 자기 시계보다 미래인 시각을 받으면 거부했습니다. 서버 시계가 조금만 늦어도 방금 로그인한 사람이 거부되고, 브라우저는 이를 로그인 만료로 받아들여 로그아웃시킬 수 있었습니다.
