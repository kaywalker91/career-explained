이용자와 보상을 서버에서 확인하고 발급 카드 값 지키기

로그인·게임 정산·카드 발급에는 서로 다른 기준이 필요했습니다. 서버의 확인과 상품 기본값, 이미 발급한 카드의 보존을 설명합니다.

GAME-004해설·근거 대조 완료해설 기준 2026-10-20

이 글의 기준과 확인 범위

사실·기여·결과의 원본은 프로젝트 기록, 서버·상품 운영 근거, 실제 업무 결과와 기여 근거입니다. 이번에는 이 기록과 해당 업무일지·계획·인계·모바일 검증 원문, 아래에 명시한 당시 코드 일부를 읽어 대조했습니다. 당시 시험·dev 배포·기기 확인은 그 시점의 기록이며 이번 제품 재실행·현재 운영 조회 결과와 구분합니다. 본인 확인과 당시 기록을 바탕으로 작성했으며, 내부 식별자는 일반 표현으로 바꿨습니다. 해설 색인

공개 코드·기록은 링크로 연결하고, 비공개 근거 기록은 제목만 표시했습니다. 본인·AI·협업자의 기여, 확인된 결과와 남은 한계를 함께 읽어 주세요.

카드로 접속한 사용자의 한 판이 관리자 기록이 되기까지

이 서비스는 원본과 바뀐 그림을 보고 다른 부분을 찾는 웹 게임입니다. 이용자는 NFC 카드를 휴대폰에 가까이 대 게임으로 들어가고, 로그인한 뒤 판을 선택해 플레이합니다. NFC는 가까이 댄 카드의 정보를 읽는 통신 방식입니다. 이 프로젝트에서는 카드 발급·접속과 플레이할 수 있는 횟수를 연결하는 데 쓰였습니다. 도전권은 한 판을 시작할 수 있는 기회이고, 포인트는 플레이 결과에 따라 받는 보상입니다. 서비스·역할 근거

휴대폰 브라우저는 그림을 보여 주고 터치를 받는 클라이언트입니다. 서버는 로그인한 사람이 누구인지, 그 사람이 해당 판을 할 수 있는지, 횟수와 포인트를 어떻게 반영할지 판단합니다. 관리자는 웹 화면에서 그림을 발행하고 상품·카드를 관리하며 플레이 기록을 확인합니다. 따라서 관리자 발행 → 휴대폰의 그림 수신 → 판 시작·플레이 → 서버 정산 → 관리자 기록의 흐름을 함께 봐야 합니다. 서버·관리자 기능에는 JavaScript와 Node.js를 사용하고, 데이터 보관에는 Firestore와 파일 저장소를 사용하는 경로가 있습니다.

같은 이용자와 같은 상품에 같은 기준을 적용하기

기존에는 브라우저가 점수·포인트를 계산해 서버에 알렸고, 별점과 다음 스테이지를 열 수 있는지는 기기에만 저장돼 있었습니다. 기기를 바꾸거나 브라우저 저장 정보를 지우면 진행 상황을 잃을 수 있고, 서버가 결과의 계산 기준을 직접 관리하기도 어려웠습니다. 로그인 때 남은 도전 횟수가 사라지는 문제도 당시 기록에 있습니다. 문제와 요구사항

카드 발급에서는 운영자가 상품 코드·횟수를 매번 입력하던 부담이 있었습니다. 상품에 정한 기본 횟수를 발급에 적용하되, 상품 설정을 나중에 바꿨다는 이유로 이미 발급한 카드의 횟수를 다시 쓰면 안 된다는 조건도 필요했습니다. 이 사건은 로그인·정산·발급의 기준을 서버에서 관리한 선별 작업을 묶습니다. 8~10월 전체 작업을 한 번에 구현·배포한 사건이라는 뜻은 아닙니다. 사건 원본

이용자 확인과 플레이 결과 계산은 다른 단계다

로그인에서 인증은 “누가 요청하는가”를 확인하는 일입니다. 카카오 로그인 경로에서는 서버가 카카오와 직접 통신해 인증 코드를 교환하고 이용자 정보를 조회한 뒤 Firebase 인증의 계정 자격으로 연결하도록 했습니다. 브라우저가 보낸 이름만으로 사용자를 정하는 대신 로그인 제공자의 확인을 거치는 흐름입니다.

그 사람이 누구인지 확인해도 아무 판의 결과나 정산해 주면 안 됩니다. 서버는 요청한 이용자의 판인지 확인한 뒤, 서버 시계·해당 판의 정답 위치·클릭 기록을 사용해 승패·별점·포인트를 계산하는 구조로 옮겼습니다. 정산은 이 결과를 계정의 보상·기록에 반영하는 처리입니다. 별점·스테이지 해금 정보도 서버에서 조회하도록 바꾼 기록이 있습니다. 로그인·정산·진행도 변경

이때 기존 점수 규칙을 유지했습니다. 이번에 읽은 당시 서버 점수 계산 코드도 화면의 별점·포인트 규칙을 서버 모듈로 옮긴 코드입니다. 계산 장소를 바꾸면서 이용자가 받는 보상 규칙까지 임의로 바꾸지 않으려는 선택입니다. 로그인 확인·판 소유 확인·결과 계산은 역할이 다르며, 이 구조만으로 모든 부정 사용이나 저장 실패가 차단됐다고 설명하지 않습니다.

상품 기본값과 이미 발급한 카드 값을 나누기

상품별 기본 도전 횟수를 등록하고, 관리자 발급 화면은 상품을 고르면 그 횟수를 보여 주도록 바꿨습니다. 발급할 때 서버가 상품 목록에서 횟수를 읽어 카드에 복사합니다. 화면에서 본 횟수와 서버의 현재 설정이 달라졌다면 발급을 중단하도록 했습니다. 예전 화면의 값을 그대로 적용해 잘못 발급하는 일을 줄이려는 처리입니다. 사용할 수 있는 상품이 없을 때는 발급 버튼도 잠그는 변경이 기록돼 있습니다. 상품·발급 변경 근거

발급 뒤에는 카드에 복사된 값과 상품의 현재 기본값을 구분해야 합니다. 같은 상품을 다시 저장할 때 횟수를 재복사하던 경로를 고쳐 이미 발급한 카드의 값을 보존했습니다. 이번에 읽은 당시 서버 변경에서도 같은 상품인지 확인한 뒤 상품 변경 처리를 건너뛰는 조건을 확인했습니다. 상품 기본값은 이후 발급의 기준이고, 기존 카드의 값은 발급 당시 부여한 값이라는 차이입니다.

여기에 NFC 코드의 일부를 발급 시각으로 추측할 수 있던 구조를 암호학적 난수, 즉 예측하기 어렵게 만든 무작위 값으로 바꾸는 작업도 연결됩니다. 카드에 기록하는 주소 길이·관리자 표시 폭을 유지하도록 코드 형식은 보존했습니다. 코드 생성 방식을 보강한 사실과 모든 카드 접근 경로의 보안 보장은 구분합니다. 상품 목록·설정 변경 안내·기존 카드 보존 조건을 함께 관리해야 하는 비용도 생깁니다. 난수·발급 기준과 한계

로그인 시각의 오차와 유지 기한을 구분하기

10월 14일에는 인증 서비스의 로그인 시각이 서버 시각보다 조금 앞서면 방금 로그인해도 거부되던 조건에 5분의 허용 오차를 뒀습니다. 이는 서로 다른 시스템의 시계 차이에 대응하는 조건이며 팀이 정한 72시간 로그인 유지 기한을 연장한 것은 아닙니다. 시계가 맞는 휴대폰에서 로그인이 유지됐다는 확인과, 서버 시계가 늦은 경계 상황을 실제로 재현한 확인도 다릅니다. 후자는 기존 자료에서 시험 정의·당시 시험 기록으로 확인한 범위입니다. 시각 조건과 결과 범위

서버·관리자 담당과 협업의 범위

본인이 서버·관리자 웹을 중심으로 담당했다는 점은 2026-10-07 사용자 확인입니다. 9월 23일 코드에는 본인 승인 시안을 참조했다는 기록이 있고, 10월 14일에는 본인의 발행 오류 제보·폴드 화면 보완 지시·일부 푸시 보류 선택이 남아 있습니다. 오류를 제보한 사실만으로 그 오류가 해결됐다고 쓰지는 않습니다.

협업자 브랜치의 회원·인증 변경, 협업자의 화면 연출, AI의 통합·구현·시험·배포·휴대폰 조작 기록도 있습니다. 이를 모두 본인의 단독 코드 작성·검증으로 합치지 않습니다. 개별 설계·구현·검토·병합·명령 실행의 세부 분담은 추가 확인입니다. 본인 역할과 협업
