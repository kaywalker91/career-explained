카드로 접속한 사용자의 한 판이 관리자 기록이 되기까지

이 서비스는 원본과 바뀐 그림을 보고 다른 부분을 찾는 웹 게임입니다. 이용자는 NFC 카드를 휴대폰에 가까이 대 게임으로 들어가고, 로그인한 뒤 판을 선택해 플레이합니다. NFC는 가까이 댄 카드의 정보를 읽는 통신 방식입니다. 이 프로젝트에서는 카드 발급·접속과 플레이할 수 있는 횟수를 연결하는 데 쓰였습니다. 도전권은 한 판을 시작할 수 있는 기회이고, 포인트는 플레이 결과에 따라 받는 보상입니다. 서비스·역할 근거

휴대폰 브라우저는 그림을 보여 주고 터치를 받는 클라이언트입니다. 서버는 로그인한 사람이 누구인지, 그 사람이 해당 판을 할 수 있는지, 횟수와 포인트를 어떻게 반영할지 판단합니다. 관리자는 웹 화면에서 그림을 발행하고 상품·카드를 관리하며 플레이 기록을 확인합니다. 따라서 관리자 발행 → 휴대폰의 그림 수신 → 판 시작·플레이 → 서버 정산 → 관리자 기록의 흐름을 함께 봐야 합니다. 서버·관리자 기능에는 JavaScript와 Node.js를 사용하고, 데이터 보관에는 Firestore와 파일 저장소를 사용하는 경로가 있습니다.

10월 2일 dev 기록에서 16:50:57 판 시작 요청 때 도전권이 7→6으로 줄었지만, 합성 그림 요청이 16초 동안 서버의 nginx에 도달하지 않았고 **16:51:13 STAGE_LOAD_FAILED**가 보고됐습니다. nginx는 여기서 그림 요청을 받는 서버 측 웹 처리 경로입니다. 이 관측은 요청이 그 지점까지 도달하지 않았다는 뜻이며 Norton 등 구체적인 네트워크 원인을 확정한 결과는 아닙니다. 변경 전 관측과 근거

환불보다 먼저 차감 시점을 바꾸기로 한 이유

당시 계획은 실제로 세 가지 방법을 비교했습니다. A안은 실패 뒤 횟수 반환, B안은 예약과 실제 시작 분리, C안은 재시도만 두고 손실은 수동 보정입니다. A안에서는 이미 시작 응답으로 정답 좌표를 받은 뒤 실패라고 주장해 환불받는 문제가 지적됐습니다. 당시 구조는 클릭 기록을 정산 때 받으므로 “아무것도 하지 않고 실패했음”을 시작 직후 서버가 입증하기 어려웠습니다.

Kay가 승인한 것은 B안입니다. 먼저 차감 없이 이번 판을 예약하고, 브라우저가 원본·합성 그림을 준비한 뒤 시작을 요청합니다. 그때 횟수를 차감하고 정답 좌표·타이머를 받습니다. 실패를 주장한 뒤 돌려받는 경로보다 실제 시작 전에는 차감하지 않는 순서를 선택한 것입니다. C안의 수동 보정은 과거 손실의 별도 처리 후보이며 이 구현이 이미 잃은 횟수를 자동 반환했다는 뜻은 아닙니다. B안 결정·제약·원문 위치 · 승인과 구현의 대응

예약·그림 준비·시작을 분리한 처리 흐름

아래는 당시 서버와 화면의 처리 순서를 압축한 설명입니다. 이번에 해당 버전의 판 예약·시작 코드와 화면 코드를 읽었으며, 현재 서비스에서 실행해 추적한 그림은 아닙니다.

예약 응답은 그림 주소를 주되 정답 좌표는 주지 않습니다. TTL은 예약을 사용할 수 있는 유효 시간이며 당시 승인값은 120초입니다. 계정당 미시작 예약 1개·분당 예약 10회 제한도 적용 기록에 있습니다. 같은 판을 재예약하면 유효한 기존 조합을 재사용해 반복 예약으로 원하는 조합을 고르는 일을 제한했습니다. 예약 저장·만료·시작 여부를 추가로 관리해야 하며 그림 자체를 비교해 정답을 추측하는 위험까지 없애는 방식은 아닙니다.

화면은 그림 준비가 실패하면 실제 시작 함수인 begin()을 부르기 전에 돌아갑니다. 당시 화면 코드는 alert 팝업과 시작 버튼 재클릭으로 재시도하며, 계획의 화면 안 [다시 시도] 버튼은 시안 검수 때문에 보류됐습니다. 만료는 한 번 재예약하는 처리가 있고 다른 실패는 상태에 맞게 안내합니다. 업무요약의 “인라인 안내 완비”를 이 버전의 실제 구현으로 옮기지 않습니다. 계획·구현 차이와 당시 인계 HC09

응답을 놓쳐 다시 눌러도 한 번만 차감하기

그림 준비 뒤 시작 요청을 보냈는데 응답만 끊겼다면, 서버에서는 이미 차감·판 생성이 끝났을 수 있습니다. 다시 요청할 때 새 판을 만들면 횟수가 한 번 더 줄어듭니다. 그래서 같은 예약의 시작을 반복하면 같은 세션을 돌려주고 추가 차감하지 않는 멱등성을 적용했습니다. 멱등성은 같은 일을 다시 요청해도 같은 처리 결과로 이어지게 하는 성질입니다.

당시 순수 판정 코드에는 예약 번호·소유 계정을 확인하고, 이미 시작된 세션이 있으면 만료 검사보다 먼저 그 세션을 재사용하는 순서가 있습니다. 미시작 예약의 만료와 이미 처리한 시작 응답의 재수신을 다르게 다루는 것입니다. 차감·세션 생성·예약의 시작 표시를 트랜잭션, 즉 함께 성공하거나 함께 반영되지 않도록 묶는 저장 처리로 연결한 구현은 기존 저장소·시험 diff 대조에 기록돼 있습니다. 파일 저장소와 Firestore 경로를 함께 다뤘다는 근거이며 모든 운영 오류가 검증됐다는 뜻은 아닙니다. 저장소 처리·시험 작성 근거

그림 준비 뒤의 시작 자체가 성공한 다음 탭을 닫거나 후속 화면 처리에 실패한 경우까지 모두 비차감이 되는 것은 아닙니다. 과거 화면과의 호환을 위해 기존 시작 경로도 남겨 둔 당시 계약입니다. “이미지 준비 전 차감 방지”를 게임의 모든 실패·모든 버전에서 무손실을 보장한다는 표현으로 바꾸지 않습니다.

재화 보호에서 본인이 결정한 범위

서버·관리자 중심 담당은 사용자 확인입니다. B안·예약 120초·계정당 제한과 문구 등은 당시 Kay의 승인 기록으로 설명합니다. 서버·클라이언트 구현과 다른 AI 세션의 작업이 함께 기록돼 있으므로, 개별 코드 작성·검토·병합·배포 명령과 클라이언트 전체를 본인 단독 수행으로 확정하지 않습니다. 변경 전 nginx 확인을 Kay의 SSH 실행으로 적은 기록도 전체 진단의 단독 수행과 구분합니다. 판단·기여·실행자 근거
