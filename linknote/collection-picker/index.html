LinkNote에서 링크를 저장하고 분류하는 과정

LinkNote는 다른 앱에서 발견한 웹 링크를 저장해 나중에 찾아보는 모바일 북마크 앱입니다. 링크와 함께 제목·설명 등을 보관하고, 관련 링크를 컬렉션이나 태그로 묶어 정리합니다. 컬렉션은 링크를 모으는 분류이고, 컬렉션 피커는 그 분류를 고르는 선택 창입니다. 화면은 Flutter로 만들고, Riverpod은 조회 상태와 화면을 연결합니다. 이 사례에서 필요한 것은 화면을 그리는 일과 데이터가 도착하는 일이 서로 다른 시점에 일어난다는 점입니다. 서비스·기술의 근거

사용자가 겪은 두 가지 불편

2026-07-29의 첫 문제는 컬렉션이 있는데도 홈의 선택 창에는 ‘없음’만 보이는 현상이었습니다. 컬렉션 탭을 방금 보고 오면 정상이기도 했습니다. 자료가 실제로 사라진 것인지, 아직 불러오지 못한 것인지 사용자는 화면만 보고 판단하기 어려웠고, 원하는 분류를 선택할 수도 없었습니다.

2026-07-30에는 링크 저장 화면의 불편을 이어 다뤘습니다. 저장 폼, 즉 URL·제목 등을 입력하는 화면에 컬렉션 선택 항목이 없어, 먼저 링크를 저장하고 홈에서 다시 분류를 옮겨야 했습니다. 첫 수정은 선택 창이 목록을 제대로 보여주는 일이고, 다음 수정은 그 창을 추가·편집 화면에서도 사용하게 하는 일이었습니다. 사건 기록

목록이 없는 것과 아직 모르는 것은 다르다

앱이 서버에 목록을 요청해도 결과가 즉시 도착하지는 않습니다. 결과를 기다리는 동안에도 앱은 선택 창을 열고 다른 화면 처리를 이어갈 수 있습니다. 이렇게 요청과 결과 도착 사이에 다른 처리를 이어가는 방식을 비동기 처리라고 합니다. 따라서 선택 창이 열리는 순간에는 ‘조회 중’, ‘조회 실패’, ‘조회 성공’을 구분해야 하고, 성공한 뒤에야 받은 항목이 0개인지 판단할 수 있습니다.

Riverpod의 provider는 이 사례에서 컬렉션 목록과 조회 상태를 화면에 제공하는 연결점입니다. 캐시는 이미 받은 데이터를 다시 쓸 수 있게 임시로 보관하는 것입니다. 기준 코드의 목록은 사용이 끝나면 해제될 수 있고(autoDispose), 링크를 다른 컬렉션으로 옮긴 뒤에는 분류별 링크 개수를 다시 조회하도록 기존 목록을 무효화합니다(invalidate). 무효화는 저장된 컬렉션을 삭제하는 일이 아니라, 화면에서 쓸 자료를 다시 가져오게 하는 일입니다. LNOTE-C02

변경 전 창은 열릴 때 ref.read로 그 순간의 상태를 한 번 읽었습니다. 그리고 아직 결과가 없거나 실패한 상태도 빈 목록으로 바꿔 그렸습니다. 창이 이후의 상태 변화를 관찰하지 않았으므로, 늦게 결과가 도착해도 이미 열린 창의 목록은 바뀌지 않았습니다. 문제의 핵심은 조회가 느리다는 사실 자체보다 기다림·실패를 빈 목록으로 합치고 그 뒤의 변화를 화면에 연결하지 않은 것입니다.

창을 열기 직전 상황 당시 데이터 상태 변경 전 창에서 생긴 일
컬렉션 탭에서 목록을 보고 옴 이미 받은 목록이 남아 있음 그 순간 읽은 목록이 표시되어 정상으로 보임
임시 데이터가 해제된 뒤 처음 열거나, 목록을 다시 조회 중 아직 결과가 도착하지 않음 항목이 없는 것처럼 그린 뒤, 결과가 와도 갱신하지 않음
조회 요청 실패 목록을 가져오지 못함 실패 안내 없이 항목이 없는 것처럼 보임

이 진입 순서의 차이는 당시 계획서의 증상·원인 분석입니다. 모든 요청이 실패했다거나 서버의 컬렉션이 삭제됐다는 뜻은 아닙니다. 당시 원인 코드와 상황표

창을 열고 나서도 결과를 받아 화면을 바꾸기

수정에서는 창 안에서 ref.watch(collectionListProvider)로 목록 변화를 계속 받게 했습니다. watch는 그 순간의 상태를 읽는 데 더해, 상태가 바뀔 때 이 데이터를 쓰는 화면을 다시 구성하도록 연결합니다. 상태를 담은 AsyncValue의 when은 조회 중·실패·성공에 맞는 화면을 선택합니다. 이 연결은 데이터를 항상 즉시 가져오게 만드는 기능이 아니라, 현재 어떤 상태인지와 나중에 바뀐 결과를 화면에 반영하는 기능입니다.

조회 중에는 돌아가는 진행 표시를 보여 기다리는 상황을 알립니다. 실패하면 ‘컬렉션을 불러오지 못했습니다’와 ‘다시 시도’를 보여줍니다. 재시도는 목록의 refresh()를 호출하며, 이 처리는 상태를 조회 중으로 바꾼 뒤 새 조회의 성공 또는 실패를 반영합니다. 재조회 때에도 기다림을 표시하도록 skipLoadingOnRefresh: false를 명시했습니다.

조회에 성공하면 분류를 해제할 수 있는 ‘없음’ 선택지와 받은 컬렉션을 표시합니다. 성공한 목록이 비어 있을 때에는 ‘컬렉션이 없어요’라는 안내를 함께 보여줍니다. ‘없음’은 사용자가 고르는 동작이고, ‘컬렉션이 없어요’는 조회 결과에 대한 안내입니다. 둘은 같은 의미로 쓰이지 않습니다. 공용 피커 코드, 목록 새로 조회 코드

홈에서 창을 여는 순서도 정리했습니다. 링크 카드의 메뉴에서 ‘컬렉션으로 이동’을 누르면 메뉴를 닫으면서 이동 의도를 결과로 돌려주고, 그 결과를 받은 쪽에서 선택 창을 엽니다. 같은 클릭 처리 안에서 메뉴 닫기와 다음 창 열기를 곧바로 실행하던 흐름을 나눈 것입니다. 기준 코드는 메뉴의 닫힘 결과를 기다리지만, 닫히는 애니메이션이 완전히 끝날 때까지 기다리지는 않습니다. 메뉴 결과와 피커 열기

왜 창 안에서 상태 변화를 받는 방법을 골랐나

당시 계획서에는 다음 세 방법의 비교가 남아 있습니다. 아래 선택 이유는 그 기록에 근거하며, 이번 학습 문서를 쓰면서 과거의 고민을 새로 만든 것이 아닙니다.

실제 검토한 방법 문제와 연결한 판단
조회가 끝날 때까지 기다린 뒤 창 열기(await future) 최초 결과를 받고 열 수 있지만 그동안 창이 뜨지 않고, 열린 뒤의 재조회 변화를 반영하는 연결은 별도로 필요함
창 안에서 상태 변화 받기(watch, 채택) 창을 바로 열어 기다림을 안내하고, 조회 완료·실패·이후 재조회도 같은 화면에서 반영할 수 있음
임시 데이터를 계속 보관하기(keepAlive) 데이터가 남아 있어 증상을 줄일 수 있지만, 이 방법만으로 실패·빈 목록을 구분하거나 열린 화면의 갱신 문제를 해결하지 못함. 앱 전체의 보관 정책도 바뀜

선택한 방법은 기존 데이터 보관·재조회 정책을 유지하면서 창의 표시 방식을 고치는 것이었습니다. 대신 창에서 상태별 화면과 재시도를 관리해야 합니다. 입력 화면에 분류를 연결할 때도 기존 선택 창을 재사용했고, 창 안에서 새 컬렉션을 만드는 기능은 당시 사용자 결정으로 제외했습니다. 실제 대안 비교, 07-30 요청과 선택 기록

분류 선택·해제·닫기를 구분하고 저장까지 연결하기

선택 창을 닫는 동작은 세 가지 의도를 가질 수 있습니다. 예를 들어 편집 중인 링크가 ‘공부’에 들어 있을 때, 다른 분류를 고르는 것과 분류를 없애는 것, 아무것도 바꾸지 않고 돌아가는 것은 다릅니다.

사용자 행동 창이 돌려주는 값 입력 화면의 처리
특정 컬렉션 선택 CollectionPick(id: 선택한 ID) 선택한 분류로 폼 상태 변경
‘없음’ 선택 CollectionPick(id: null) 폼의 분류를 해제
선택하지 않고 창 닫기 null 기존 폼의 분류 유지

여기서 ID는 컬렉션을 구분하는 고유값이고, null은 값이 없음을 뜻합니다. ID만 반환하면 ‘분류 해제’와 ‘선택하지 않고 닫기’가 모두 null이 되어 두 의도를 구분할 수 없습니다. 그래서 선택했다는 사실을 담는 결과 객체(CollectionPick) 안에 ID를 넣었습니다. 객체가 있고 그 안의 ID가 비었으면 해제이고, 객체 자체가 없으면 닫기입니다. 입력 화면은 먼저 결과 객체가 있는지 확인하고, 있을 때만 폼 상태를 바꿉니다. 선택 결과·폼 반영 코드

저장 화면을 연결할 때에는 먼저 기존 코드가 어디까지 갖춰져 있는지 확인했습니다. 당시 기록의 git grep 결과는 updateCollectionId의 정의와 테스트 호출을 보여줬고, 선택값을 실제 입력 화면에서 바꾸는 호출은 연결되지 않은 상태였습니다. 반면 폼의 collectionId를 저장 데이터에 담아 생성·수정으로 보내는 경로는 이미 있었습니다. 따라서 작업은 서버 저장 구조를 새로 만드는 대신 사용자가 값을 고르는 화면과 기존 저장 경로를 연결하는 것으로 좁혔습니다. PR #73의 해당 업무 규칙·데이터 처리 경로 diff가 0줄이라는 기존 대조도 이 범위를 뒷받침합니다. LNOTE-C04

추가·편집 화면에서의 변경 후 흐름은 다음과 같습니다.

  1. 사용자가 폼의 컬렉션 항목을 누르면 공용 선택 창을 엽니다. 이 창은 홈에서 쓰던 선택 창을 여러 화면에서 사용할 수 있도록 옮긴 것입니다.
  2. 선택 결과 객체가 돌아오면 그 안의 ID를 updateCollectionId로 폼 상태에 넣습니다. 창만 닫았다면 이 변경을 건너뜁니다. 이 시점에는 저장 버튼을 누르기 전 폼의 선택값이 바뀐 것입니다.
  3. 화면은 폼의 선택값에 맞는 컬렉션 이름을 표시합니다. ID는 있지만 지금 받은 목록에서 이름을 찾지 못하면 ‘없음’이라고 단정하지 않고 ‘선택한 컬렉션’으로 표시해 값을 유지합니다.
  4. 사용자가 저장을 누르면 submit()이 URL·제목 등 필수 입력을 확인하고, 폼의 collectionId를 링크 저장 데이터인 LinkEntity에 함께 넣습니다.
  5. 새 링크면 기존 생성 처리로, 기존 링크면 기존 수정 처리로 전달합니다. 선택값이 기존 저장 흐름에 포함되므로 저장 뒤 다시 홈에서 분류를 옮기는 단계를 줄일 수 있게 연결한 것입니다. 실제 시간 단축량은 측정하지 않았습니다.

추가·편집 화면은 같은 입력 필드 묶음인 LinkFormFields를 사용합니다. 다른 앱이 공유한 URL을 받아 여는 링크 추가 화면도 이 공용 필드를 쓰므로 코드상 연결 범위에 포함됩니다. 홈에서 이미 저장한 링크를 옮기는 경우에는 선택값을 폼에 보관하는 대신 기존 이동 처리를 호출합니다. 이 코드 연결을 각 진입 경로의 실기기 시험 통과로 확대하지 않습니다. 폼·추가/편집 화면 연결 근거, 기존 저장 처리
