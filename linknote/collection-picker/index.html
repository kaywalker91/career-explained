LinkNote에서 링크를 저장하고 분류하는 과정

LinkNote는 다른 앱에서 발견한 웹 링크를 저장해 나중에 찾아보는 모바일 북마크 앱입니다. 링크와 함께 제목·설명 등을 보관하고, 관련 링크를 컬렉션이나 태그로 묶어 정리합니다. 컬렉션은 링크를 모으는 분류이고, 컬렉션 피커는 그 분류를 고르는 선택 창입니다. 화면은 Flutter로 만들고, Riverpod은 조회 상태와 화면을 연결합니다. 이 사례에서 필요한 것은 화면을 그리는 일과 데이터가 도착하는 일이 서로 다른 시점에 일어난다는 점입니다. 서비스·기술의 근거

사용자가 겪은 두 가지 불편

저장해 둔 링크를 다른 분류로 옮기려면 홈의 링크 메뉴에서 ‘컬렉션으로 이동’을 누릅니다. 그런데 컬렉션이 있는데도 선택 창에는 ‘없음’만 보였습니다. 컬렉션 탭을 보고 돌아오면 목록이 나타나기도 했습니다. 같은 작업인데 앞서 어떤 화면을 봤는지에 따라 원하는 분류를 고를 수 있기도, 없기도 한 문제였습니다. 2026-07-29 기록에 남은 증상입니다.

저는 목록이 비어 보이는 원인을 분석하고, 화면을 갱신하는 방식을 설계·구현한 뒤 시험과 실기기 확인을 맡았습니다. 다음 날에는 같은 선택 창을 링크 추가·편집 화면에도 연결했습니다. 이 두 변경의 분석·설계·구현·테스트·실기기 확인을 모두 본인이 담당했다는 내용은 2026-10-08 사용자 확인입니다. PR #73에는 Claude 공동 작성도 표기돼 있습니다. 본인 담당과 AI 협업을 함께 남기며, 개별 코드·시험의 AI 작성 범위와 업로드 담당은 추가 확인입니다. 담당 확인 · 관련 커밋 대조

두 번째 변경은 링크를 처음 저장하는 순간의 불편을 줄이려는 작업이었습니다. URL·제목 등을 입력하는 저장 폼에 분류 선택 항목이 없어, 먼저 저장한 뒤 홈에서 다시 분류를 옮겨야 했습니다. 따라서 선택 창의 목록을 바로잡는 데서 이어, 사용자가 저장·편집 중에도 그 창을 열 수 있게 했습니다. 창 안에서 새 컬렉션을 만드는 기능은 당시 사용자 결정으로 제외했습니다. 사건 기록 · 저장 시 선택 요청과 결정

목록이 없는 것과 아직 모르는 것은 다르다

먼저 선택 창이 목록을 읽는 시점을 살폈습니다. 앱이 서버에 목록을 요청해도 결과가 즉시 도착하지는 않습니다. 응답을 기다리는 동안에도 창은 열릴 수 있습니다. 이처럼 요청을 보낸 뒤 다른 처리를 이어가는 것을 비동기 처리라고 합니다. 창이 열렸다는 사실만으로는 목록을 다 받았는지 알 수 없었습니다.

변경 전 코드는 ref.read로 창을 열 때의 조회 상태를 한 번 읽었습니다. 아직 결과가 없거나 조회에 실패해도 이를 빈 목록으로 바꿔 그렸습니다. 그 뒤 상태가 달라지는지 받는 연결도 없었으므로, 응답이 도착해도 열린 창은 그대로였습니다. 조회 중·실패·정상 빈 목록을 같은 화면으로 만들고, 늦게 온 결과도 반영하지 않는 두 문제가 겹쳤습니다.

창을 열기 직전 상황 당시 데이터 상태 변경 전 창에서 생긴 일
컬렉션 탭에서 목록을 보고 옴 이미 받은 목록이 남아 있음 그 순간 읽은 목록이 표시되어 정상으로 보임
임시 데이터가 해제된 뒤 처음 열거나, 목록을 다시 조회 중 아직 결과가 도착하지 않음 항목이 없는 것처럼 그린 뒤, 결과가 와도 갱신하지 않음
조회 요청 실패 목록을 가져오지 못함 실패 안내 없이 항목이 없는 것처럼 보임

다른 탭을 보고 왔을 때만 정상이던 이유도 여기서 설명됩니다. Riverpod의 provider는 목록과 조회 상태를 화면에 제공하는 연결점입니다. 이미 받은 자료를 임시로 보관하는 캐시가 살아 있으면, 한 번만 읽어도 목록을 얻을 수 있었습니다. 반대로 기준 코드는 목록을 쓰는 화면이 사라지면 상태를 해제할 수 있고(autoDispose), 링크 이동 뒤에는 분류별 개수를 갱신하려고 목록을 다시 조회하게 합니다(invalidate). 이때 창을 열면 아직 응답을 기다리는 상태를 읽을 수 있었습니다. 재조회는 서버의 컬렉션을 지우는 처리가 아닙니다. 이 설명은 당시 계획의 원인 분석과 기준 코드에 근거하며, 모든 조회가 실패했다는 뜻으로 넓히지 않습니다. 당시 원인 코드와 상황표 · 보관·재조회 근거 LNOTE-C02

창을 열고 나서도 결과를 받아 화면을 바꾸기

저는 창 안에서 ref.watch(collectionListProvider)로 목록 상태를 계속 받게 바꿨습니다. watch는 현재 값을 읽고, 나중에 그 값이 바뀌면 해당 화면을 다시 그리도록 연결합니다. 이제 창을 열 때 응답이 없어도 기다림을 표시하다가 결과가 오면 목록으로 바꿀 수 있었습니다. 서버 응답을 빠르게 만드는 수정이 아니라, 응답 전후의 화면을 실제 상태에 맞추는 수정이었습니다.

조회 상태를 담은 AsyncValue의 when으로 기다림·실패·성공에 맞는 화면을 골랐습니다. 조회 중에는 진행 표시를, 실패하면 ‘컬렉션을 불러오지 못했습니다’와 ‘다시 시도’를 보여 줍니다. 재시도를 누르면 refresh()가 상태를 조회 중으로 바꾼 뒤 새 요청의 성공 또는 실패를 반영합니다. 다시 조회할 때도 진행 표시를 보이도록 skipLoadingOnRefresh: false를 명시했습니다.

성공한 경우에는 분류를 해제하는 ‘없음’ 선택지와 받은 목록을 표시합니다. ‘컬렉션이 없어요’ 안내는 조회에 성공했고 받은 항목이 0개일 때만 함께 보여 줍니다. 따라서 사용자가 분류를 해제하려고 누르는 ‘없음’과, 조회 결과를 알려 주는 빈 목록 안내가 구분됩니다. 공용 피커 코드 · 다시 조회하는 처리

홈에서 두 창을 잇는 순서도 손봤습니다. 이전에는 메뉴의 같은 클릭 처리 안에서 메뉴를 닫고 바로 선택 창을 열었습니다. 변경 뒤에는 ‘컬렉션으로 이동’이라는 결과를 돌려주며 메뉴를 닫고, 그 결과를 받은 쪽에서 다음 창을 엽니다. 메뉴 닫기의 결과를 기다리도록 나눴지만, 닫히는 애니메이션의 완전 종료까지 기다리는 구현은 아닙니다. 메뉴 결과를 받아 피커 열기

왜 창 안에서 상태 변화를 받는 방법을 골랐나

목록이 준비된 뒤에만 창을 열거나, 이미 받은 데이터를 계속 남기는 방법도 당시 계획에서 비교했습니다. 선택 기준은 처음 한 번 목록을 보여 주는 데서 끝나지 않고, 기다림과 실패를 알리고 재조회 뒤에도 같은 창을 갱신할 수 있는가였습니다.

실제 검토한 방법 문제와 연결한 판단
조회 완료 뒤 창 열기(await future) 처음에는 결과를 받고 열 수 있지만 그동안 창이 뜨지 않음. 열린 뒤의 재조회 변화는 별도로 연결해야 함
창 안에서 상태 변화 받기(watch, 채택) 창을 바로 열어 기다림을 알리고, 조회 완료·실패·재조회 결과를 같은 화면에 반영할 수 있음
임시 데이터를 계속 보관하기(keepAlive) 증상을 줄일 수 있으나 이 방법만으로 실패와 빈 목록을 구분하거나 열린 창을 갱신하지는 못함

임시 데이터를 계속 남기려면 앱의 보관 정책도 바꿔야 했습니다. 저는 창에서 변화를 받는 방법을 적용해 기존 데이터 해제·재조회 정책을 유지했습니다. 링크 이동 뒤 분류별 개수를 새로 가져오는 처리도 남겼습니다. 대신 창 안에서 상태별 화면과 재시도를 다루는 코드가 필요해졌습니다. 이 선택 이유는 당시 대안 비교와 구현 범위를 풀어 쓴 것이며, 기록에 없는 고민을 추가하지 않습니다. 당시 대안 비교

분류 선택·해제·닫기를 구분하고 저장까지 연결하기

선택 창을 바로잡은 다음에는 저장 폼을 확인했습니다. 당시 조사 기록의 git grep은 updateCollectionId의 정의와 테스트 호출만 보여 줬습니다. 사용자가 고른 분류를 폼에 넣는 화면의 호출이 연결되지 않은 상태였습니다. 반면 폼의 collectionId를 링크 저장 데이터에 담아 생성·수정으로 보내는 경로는 이미 있었습니다. PR #73의 해당 업무 규칙·데이터 처리와 링크 provider 경로 diff도 0줄이라는 기존 대조가 있습니다. 저는 기존 저장 경로에 선택 화면을 연결하는 범위로 작업했습니다. 기존 경로와 변경 범위 LNOTE-C04

홈에서 쓰던 선택 창을 여러 화면이 함께 쓰는 공용 코드로 옮기고, 추가·편집 화면이 공통으로 쓰는 LinkFormFields에 컬렉션 항목을 넣었습니다. 사용자가 그 항목을 누르면 같은 선택 창이 열립니다. 이때 창에서 돌아오는 결과에는 세 가지 의도가 담겨야 했습니다. 편집 중인 링크가 ‘공부’ 분류에 있다면, 다른 분류를 고르기·분류 해제·아무것도 바꾸지 않고 닫기는 서로 다른 행동입니다. ‘공부’는 설명용 예시입니다.

ID는 컬렉션을 구분하는 고유값이고, null은 값이 없음을 뜻합니다. ID만 돌려주면 ‘없음’을 고른 경우와 창만 닫은 경우가 모두 null이 됩니다. 그래서 선택했다는 결과인 CollectionPick 안에 ID를 담는 구조를 사용했습니다. 결과 자체가 없으면 취소이고, 결과가 있지만 ID가 비었으면 분류 해제입니다. 폼은 결과가 있을 때만 updateCollectionId로 선택값을 바꿉니다. 이 시점에는 입력 중인 값만 달라지고, 아직 링크를 저장한 것은 아닙니다. 결과 구분과 폼 반영

폼에는 선택한 분류의 이름을 보여 줍니다. ID는 있는데 지금 받은 목록에서 이름을 찾지 못하면 ‘선택한 컬렉션’이라고 표시하고 값을 유지합니다. 이름을 못 찾았다는 이유로 ‘없음’이라고 표시하거나 기존 분류를 지우지 않도록 한 것입니다.

사용자가 저장을 누르면 기존 submit()이 URL·제목 등 필수 입력을 확인하고, 폼의 collectionId를 링크 저장 데이터인 LinkEntity에 함께 담습니다. 새 링크는 생성 처리로, 기존 링크는 수정 처리로 보냅니다. 사용자는 저장 전에 분류까지 정할 수 있게 됐고, 저장 후 홈에서 다시 옮기는 작업을 줄일 수 있는 연결을 만들었습니다. 실제 시간 단축량은 측정하지 않았습니다. 기존 저장 처리

다른 앱에서 공유한 URL로 열린 추가 화면도 같은 공용 필드를 쓰므로 코드상 연결 범위에 포함됩니다. 홈에서 이미 저장한 링크를 옮길 때에는 폼에 임시로 담는 과정을 거치지 않고 기존 이동 처리를 호출합니다. 이 연결 범위를 편집·공유 등 모든 경로의 실기기 시험 통과로 바꾸지는 않습니다. 추가·편집과 공유 경로의 근거
