공유 수신과 로그인 확인 사이에 주소를 보관하는 이유

다른 앱의 공유 요청을 받는 연결 도구가 receive_sharing_intent입니다. 앱이 꺼져 있었다면 시작 과정에서 첫 공유 내용을 읽고, 이미 실행 중이라면 이후 도착하는 공유 알림을 받습니다. 이를 코드와 기록에서는 각각 cold·warm 경로라고 부릅니다. 로그인된 계정이 기기에 남아 있어도, 앱을 새로 시작할 때에는 로그인 상태를 확인하는 시간이 필요합니다.

GoRouter는 현재 로그인 상태와 화면에 따라 다음 목적지를 정하는 화면 이동 도구입니다. 아직 로그인 확인 중이면 시작 화면에서 기다리고, 미로그인이면 로그인 화면으로 보냅니다. 이 확인을 기다리는 동안에도 공유 주소를 잃지 않도록 대기 URL 상태(pendingSharedUrlProvider)에 주소를 보관합니다. Riverpod은 이 상태를 앱 안에서 읽고 바꿀 수 있도록 연결합니다. 대기 URL은 서버에 저장한 북마크가 아니라, 입력 화면에 전달할 때까지 메모리에 남겨 두는 한 건의 주소입니다.

처음의 데이터 형식 가설에서 URL을 지우는 시점으로 원인을 좁히기

처음에는 YouTube가 보내는 공유 데이터 형식을 의심했습니다. 공유 연결 도구에서 주소를 읽지 못했을 가능성에 대비해, Android가 전달하는 텍스트 항목인 EXTRA_TEXT 등에서 URL을 추가로 읽는 대체 경로를 넣었습니다. 그러나 +6 내부테스트에서도 같은 문제가 남았습니다. 이 시도는 실제로 수행한 대응이며, 최종 원인을 해결한 방법으로 설명하지 않습니다.

이후 진단 기록에는 URL을 정상적으로 읽은 결과인 resolvedUrl까지 확보했다고 적혀 있습니다. 문제는 그 뒤 목적지를 정하는 과정이었습니다. 로그인 상태 갱신 알림이 여러 번 발생하면서 GoRouter의 redirect, 즉 다음 화면을 정하는 판단도 반복됐습니다. 첫 판단이 대기 URL을 지우고 입력 화면을 목적지로 돌려줬지만, 아직 시작 화면에 있는 다음 판단에서는 대기 URL이 비어 있어 홈으로 보내는 흐름이었습니다. 이를 순서 경쟁이라고 부릅니다. 각각의 처리가 실행돼도 그 순서에 따라 필요한 정보가 먼저 사라지는 문제입니다. 당시 진단과 해결 기록

입력 화면에 도착한 뒤 정리하고 내용을 채우기

아래는 대기 URL을 사용하는 앱 시작·미로그인 공유 경로의 변경 후 흐름입니다. 실행 중 로그인된 사용자가 바로 입력 화면을 여는 경우에는 앞 표처럼 대기 상태를 거치지 않고 URL을 전달합니다.

처리 순서를 조금 더 풀면 다음과 같습니다.

  1. URL을 화면에 전달합니다. 목적지 주소의 prefill이라는 입력값에 URL을 넣습니다. URL 안의 ?·& 같은 문자가 목적지 주소의 구분자로 섞이지 않도록 인코딩, 즉 전달용 표현으로 바꿉니다. LinkAddScreen은 전달받은 URL을 자기 입력란에 넣습니다.
  2. 대기 URL을 정리합니다. 첫 화면 구성이 끝난 뒤 실행하는 addPostFrameCallback에서 consume()을 호출합니다. consume()은 대기값을 비우는 처리입니다. 화면 생성 중에는 Riverpod 상태를 바꾸지 않도록 실행 시점을 뒤로 옮겼습니다. 이때 주소는 이미 화면이 전달받았으므로, 대기값을 지우는 일과 화면의 주소를 지우는 일은 다릅니다. 대기값 정리는 입력 화면 도착을 기준으로 하며 저장 성공을 뜻하지 않습니다.
  3. 입력 상태가 준비된 뒤 링크 정보를 조회합니다. 화면의 텍스트 입력란과 저장에 사용할 폼 상태는 별도로 준비됩니다. 폼 상태가 아직 준비 중이면 정보 조회 요청이 처리되지 않을 수 있어, 준비 완료를 기다린 뒤 URL을 반영하고 OG를 한 번 조회합니다. OG(Open Graph)는 웹페이지가 제공하는 제목·설명·이미지 정보로, 사용자가 내용을 모두 직접 쓰는 수고를 줄입니다.
  4. 늦은 응답으로 사용자가 쓴 내용을 덮지 않습니다. 조회를 기다리는 동안 제목 등을 직접 쓸 수 있으므로, 응답이 도착하면 그때의 최신 폼 상태를 다시 읽어 빈 항목만 채웁니다. 예를 들어 사용자가 이미 제목을 썼다면 사이트에서 받은 제목으로 바꾸지 않습니다. 조회에 실패하거나 받은 제목이 비어 있으면, 사용자 제목이 비어 있는 경우에만 youtube.com처럼 URL의 사이트 주소 부분을 임시 제목으로 씁니다. 이 주소는 설명용 예시이며, 실패한 조회 자체가 성공한 것으로 바뀌는 것은 아닙니다.

화면 도착·준비 대기는 입력 화면 코드, 빈 항목 채우기·대체 제목은 폼 처리 코드와 대조했습니다. 대기 상태 파일의 ‘redirect에서 소비’라는 주석은 실제 화면 도착 후 정리 코드와 다릅니다. 해설은 직접 읽은 구현을 따릅니다. 주석 불일치의 기존 대조

사용자가 저장한 뒤 돌아갈 화면까지 처리하기

URL만 보이는 화면으로는 작업이 끝나지 않습니다. 기준 폼은 저장할 때 URL과 제목을 확인하므로, 링크 정보 조회와 임시 제목은 사용자가 저장을 이어갈 수 있게 하는 처리이기도 합니다. 사용자가 최종 내용을 확인하고 저장을 누르면 기존 저장 처리를 실행합니다. 공유 수신이나 대기값 정리만으로 서버에 링크를 만들지 않습니다.

저장이 성공하면 성공 안내를 보여 주고 canPop()으로 돌아갈 이전 화면이 있는지 확인합니다. 이미 실행 중인 앱에서 입력 화면을 새로 열었다면 이전 화면으로 돌아갈 수 있지만, 앱 시작 직후 목적지 전환으로 도착했다면 뒤로 돌아갈 화면이 없을 수 있습니다. 그래서 이전 화면이 있으면 pop()으로 복귀하고, 없으면 go(home)으로 홈을 엽니다. 저장 실패 때에는 이 복귀 분기를 실행하지 않습니다. 입력 화면 진입과 저장, 저장 후 복귀를 나눠 살펴야 하는 이유입니다. 저장 후 복귀 코드
