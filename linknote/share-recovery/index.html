앱은 열렸는데 저장할 주소가 이어지지 않았다

LinkNote는 다른 앱에서 발견한 링크를 보관해 나중에 찾아보는 모바일 앱입니다. YouTube에서 영상을 보다가 공유 메뉴의 LinkNote를 고르면, 영상 주소가 들어 있는 링크 추가 화면이 열려야 했습니다. 사용자는 그곳에서 제목과 내용을 확인한 뒤 저장합니다. 그런데 2026-07-22 기록에서는 로그인된 상태로 공유해도 앱만 열리고 이 입력 화면으로 이어지지 않았습니다. 링크를 발견한 자리에서 저장하려던 사용자가 다음 단계로 갈 수 없는 문제였습니다.

저는 이 문제의 원인을 판단하고 코드를 수정한 뒤 실제 기기에서 확인했습니다. 이 세 범위를 모두 맡았다는 점은 2026-10-08 사용자 확인이며, 관련 변경에는 Claude 공동 작성도 표기돼 있습니다. 당시에는 케이블 없이 Play 내부테스트 빌드를 받아 확인했습니다. 먼저 보낸 +5·+6 빌드에서도 같은 실패가 남아, 앱이 열리는지만 볼 것이 아니라 주소가 어느 단계에서 이어지지 않는지 좁혀야 했습니다. 본인 담당 확인 · 당시 증상·빌드 기록

공유 수신과 로그인 확인 사이에 주소를 보관하는 이유

앱이 꺼진 상태에서 공유를 받으면 앱을 시작하는 동안 주소를 읽습니다. 이때 기기에 로그인 정보가 남아 있어도 실제 로그인 상태를 확인하는 시간이 필요합니다. 확인이 끝나기 전에 주소를 버리면, 다음 화면을 정할 때 어떤 링크를 저장하려 했는지 알 수 없습니다. 그래서 기존 코드는 입력 화면으로 넘길 주소를 메모리에 잠시 보관했습니다. 이 대기 URL은 아직 저장한 북마크가 아니라 전달을 기다리는 주소 한 건입니다.

외부 앱의 공유를 받는 도구는 receive_sharing_intent이고, 다음 화면을 정하는 도구는 GoRouter입니다. GoRouter는 로그인 확인 중이면 시작 화면에서 기다리게 하고, 로그인이 필요하면 로그인 화면으로 보냅니다. Riverpod의 pendingSharedUrlProvider는 이 과정에서 같은 대기 주소를 읽고 바꾸도록 연결하는 상태입니다. 이미 실행 중인 앱에서 미로그인 상태로 공유를 받아도 여기에 주소를 넣어 로그인 뒤 이어갑니다. 코드와 기록에서 앱 시작 수신을 cold, 실행 중 수신을 warm이라고 부르는 이유도 이 진입 조건의 차이입니다.

반면 실행 중이고 로그인도 끝났다면 주소를 입력 화면에 바로 전달할 수 있습니다. 이미 링크 추가·컬렉션 생성·편집 화면에서 작성하고 있다면 곧바로 화면을 바꾸지 않고 ‘공유한 링크를 받았어요’ 안내와 ‘열기’ 버튼을 보여 줍니다. 사용자가 버튼을 눌러 새 입력 화면을 열게 하여 기존 작성을 방해하지 않는 처리입니다. 기존 폼에 새 공유 내용을 자동으로 합치지는 않습니다. 주소를 찾지 못했을 때에는 실패 안내를 보여 줍니다. 이 분기는 기준 코드에서 확인한 동작이며, 모든 상황의 실기기 성공을 뜻하지 않습니다. 시작 시 주소 보관 · 실행 중 수신·입력 보호

처음의 데이터 형식 가설에서 URL을 지우는 시점으로 원인을 좁히기

처음에는 YouTube가 보내는 데이터 형식을 의심했습니다. 공유를 받는 도구가 영상 주소 대신 다른 내용을 읽었을 가능성이 있었기 때문입니다. Android가 전달하는 텍스트 항목인 EXTRA_TEXT 등에서도 주소를 읽는 대체 경로를 추가했지만, +6 내부테스트에서도 같은 문제가 남았습니다. 이 시도만으로는 실제 실패를 해결하지 못했습니다.

이후 진단을 위해 정보를 표시한 빌드에서는 주소를 읽은 결과인 resolvedUrl까지 정상이라는 기록을 얻었습니다. 주소를 받기 전이 아니라 받은 뒤의 이동 과정으로 조사 범위를 좁힐 수 있었습니다. 그 과정에서 로그인 상태가 갱신될 때 GoRouter의 redirect, 즉 다음 화면을 정하는 판단이 여러 번 실행되는 점을 확인했습니다. 첫 판단은 대기 URL을 지우고 입력 화면으로 가라는 결과를 돌려줬습니다. 그러나 화면이 바뀌기 전에 다음 판단이 실행되면 주소가 이미 비어 있어 홈으로 보내고 있었습니다. 처리가 실행되는 순서에 따라 결과가 달라지는 순서 경쟁이었습니다. 실패한 시도와 후속 진단

저는 목적지를 판단할 때 주소를 지우는 처리를 빼고, 입력 화면이 주소를 받은 뒤 지우도록 옮겼습니다. 화면이 도착하기 전까지는 같은 주소를 보존하므로, 판단이 반복돼도 같은 입력 화면을 목적지로 돌려줄 수 있습니다.

입력 화면에 도착한 뒤 정리하고 내용을 채우기

입력 화면이 주소를 받았다고 곧바로 링크가 저장되는 것은 아닙니다. 먼저 주소를 화면에 채우고, 사용자가 내용을 확인할 수 있도록 제목·설명 등을 준비해야 했습니다. 대기 URL을 거치는 앱 시작·미로그인 공유 경로는 다음과 같이 이어집니다. 실행 중 이미 로그인된 경우에는 앞서 설명한 대로 대기 상태를 거치지 않고 입력 화면을 엽니다.

화면을 여는 주소의 prefill 입력값에 공유 URL을 담습니다. URL 안의 ?·&가 화면 주소의 구분자와 섞이지 않도록 전달용 표현으로 바꾸는 것이 인코딩입니다. LinkAddScreen은 이렇게 전달받은 URL을 자기 입력란에 넣습니다. 주소가 화면에 넘어온 뒤에는 원래 대기값을 지워도 입력란의 주소는 남습니다.

대기값을 비우는 consume()은 첫 화면 구성이 끝난 뒤 실행하는 addPostFrameCallback 안으로 옮겼습니다. 화면을 만드는 중에는 Riverpod 상태를 바꾸지 못하는 제약도 있어 실행을 뒤로 미룬 것입니다. 대기값 정리는 입력 화면 도착을 기준으로 하며, 저장 성공 표시가 아닙니다.

화면의 입력란과 실제 저장에 쓸 폼 상태도 따로 준비됩니다. 폼 상태가 준비되기 전에 링크 정보를 조회하면 요청이 처리되지 않을 수 있어, 준비 완료를 기다린 뒤 URL을 넣고 정보를 한 번 조회하도록 했습니다. 여기서 조회하는 OG(Open Graph)는 웹페이지가 제공하는 제목·설명·이미지 정보입니다. 사용자가 모든 내용을 직접 쓰지 않아도 되게 돕습니다. 주소 전달·화면 도착 후 정리·준비 대기
