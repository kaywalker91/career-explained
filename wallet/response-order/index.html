사용자가 외부 지갑과 앱을 오가는 과정

지갑 연결 앱는 외부 암호화폐 지갑을 연결해 자산과 거래 활동을 보는 모바일 앱입니다. 지갑을 추가하려면 사용자는 지갑 연결 앱에서 외부 지갑 앱으로 이동해 연결을 승인하거나 서명한 뒤 돌아옵니다. 그런데 사용자가 앱으로 돌아온 시점과 연결에 필요한 응답이 도착한 시점은 다를 수 있습니다. 돌아올 앱이 꺼져 있다면 앱을 새로 시작하면서 응답도 넘겨받아야 합니다. 기존 이력서에는 이 과정의 연결 실패, 앱이 꺼진 상태의 연결 단절, 네트워크 변화나 사용자 중단에 대한 대응이 기록돼 있습니다. 프로젝트와 당시 문제

지갑 연결은 서비스 앱 안에서만 끝나지 않습니다. 사용자는 MetaMask나 Trust Wallet을 열어 연결을 승인하고, 지갑 소유자라는 증거인 서명을 만든 뒤 서비스로 돌아옵니다. 서비스는 지갑의 응답과 서버의 인증 정보를 받아 다음 화면으로 진행해야 합니다. 앱 복귀·승인·서명·서버 조회가 같은 순서로 끝난다는 보장은 없습니다.

당시 문제 문서에는 MetaMask에서 돌아올 때 앱이 종료되는 문제, Trust Wallet에서 승인해도 서명 요청이 시작되지 않는 문제, 서명 뒤 오류 없이 멈추는 문제와 QR 창이 남는 문제가 있습니다. 겉으로는 모두 ‘연결이 안 된다’로 보이지만, 고칠 지점은 달랐습니다. 당시 문제 기록

앱 복귀를 여러 곳이 동시에 처리하지 않게 한다

MetaMask 문제 기록의 원인은 링크 수신·상태 관리·데이터 처리 쪽에서 통신 중계 서버인 Relay에 각각 재연결을 요청한 것이었습니다. 앱이 돌아왔다는 하나의 상황을 여러 곳이 처리하면서 같은 연결을 동시에 열려고 했습니다.

수정 코드는 앱 복귀 때의 재연결을 공통 링크 서비스에 모으고, 이미 실행 중이면 같은 처리를 겹쳐 실행하지 않는 장치를 둡니다. 코드 이름은 SingleExecutionGuard입니다. 지갑별 차이를 받는 어댑터에도 중복 콜백을 막는 처리를 연결했습니다. 어댑터는 각 지갑의 응답을 앱이 다루는 공통 방식으로 바꾸는 부분입니다. 재연결 코드 · 수정 커밋

한 곳에서 재연결을 맡도록 정리한 대신, 다른 연결 경로도 이 담당 부분과 맞춰야 합니다. 코드에는 최대 세 번의 시도가 있지만 실패를 기록하고도 다음 주소 처리가 이어질 수 있습니다. 중복 실행 제한을 네트워크 복구의 성공 보장으로 설명하지 않는 이유입니다. 앞의 복귀 중 링크 처리 기록와 함께 읽을 수 있습니다.

승인 단계와 인증 정보 중 어느 것이 먼저 와도 살핀다

Trust Wallet에서 연결 승인이 끝났어도 서명을 요청하려면 서버의 Nonce가 필요합니다. Nonce는 그 인증 요청을 위해 받은 일회성 값입니다. 승인 단계와 Nonce가 각각 다른 시점에 바뀌는데 한쪽 변화만 보면, 필요한 정보가 나중에 도착해도 요청을 시작하지 못할 수 있습니다. 당시 문서는 화면 상태 갱신 전의 오래된 단계를 읽는 문제를 원인으로 기록합니다.

구현은 두 변화를 따로 받습니다. 인증 대기 단계에 들어오면 Nonce가 준비됐는지 확인하고, Nonce가 늦게 오면 그 변화를 받는 경로에서 현재 단계를 다시 확인합니다. 둘 다 이미 서명 중인지 확인하며, 만료된 값이면 새 값을 요청합니다. 단계 변화 경로에는 Nonce의 주소와 지금 추가하려는 주소가 같은지 비교하는 검사도 있습니다. 확인한 조건의 범위이며 모든 응답 순서·잘못된 인증 정보를 완전히 차단했다는 실행 결과는 아닙니다. 두 수신 경로와 검사

조회를 기다리는 동안 받은 새 서명을 남긴다

다른 MetaMask 문제는 서명이 왔는지보다 그 서명이 뒤의 상태 갱신에도 남는지가 핵심이었습니다. 연결 상태를 확인하는 함수는 조회를 시작할 때의 상태를 기억하고 서버 처리를 기다립니다. 그 사이 지갑에서 서명이 도착해도, 조회 완료 뒤 처음 기억한 상태를 다시 쓰면 새 서명이 사라질 수 있습니다. 이것이 서명 유실 문제 문서에 기록된 원인입니다.

수정은 성공한 조회 결과를 반영하기 직전에 현재 상태를 다시 읽습니다. 가장 최근의 서명·주소가 있으면 이를 조회 결과에 합칩니다. 이처럼 기다리는 동안 바뀐 값을 함께 반영하는 처리를 병합이라고 합니다.

코드는 최신 값이 null이면 이전 값을 사용합니다. 따라서 새 서명·주소 보존을 다룬 변경이며, 모든 상태 필드의 동시 갱신이나 값을 의도적으로 비운 상황까지 해결했다는 뜻은 아닙니다. 조회 실패도 별도 오류 경로로 남습니다. 상태 조회·최신 값 병합

QR 창은 열었던 관리자에서 닫는다

QR은 다른 기기의 지갑으로 연결할 주소를 보여 주는 창입니다. 연결이 끝났는데 이 창이 남으면 사용자는 다음 동작을 가린 화면을 보게 됩니다. 당시 코드는 앱 전체의 화면 관리자에서 창을 열고, 안쪽 화면의 관리자에 닫기를 요청해 창을 찾지 못했습니다. Flutter의 Navigator가 화면과 창의 이동을 관리하는 부분입니다.

수정에서는 열기와 닫기 모두 앱 전체의 관리자, 즉 루트 Navigator를 지정합니다. 실제 닫기를 요청한 뒤 표시 상태를 정리하고, 성공뿐 아니라 오류·취소·시간 초과로 복귀한 경우도 닫기 조건에 포함했습니다. 창 표시·닫기

재시도 가능한 오류에서도 QR 창이 닫히므로 다시 연결을 시작해야 하는 비용이 있습니다. 창 잔류를 해결한 처리와 기존 QR을 유지한 채 재시도하는 경험은 구분해야 합니다. 당시 검토에 남은 재시작 비용
