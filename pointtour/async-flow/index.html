포인트투어에서 방문과 매장 이용을 연결하는 과정

포인트투어는 장소를 방문하거나 매장을 이용하는 활동을 포인트·혜택에 연결하는 서비스입니다. 이용자가 쓰는 앱과 매장 운영자가 쓰는 앱이 있고, Android·iOS의 화면·서버 응답·현장 운영이 이어져야 합니다. 아래 두 사례는 통신 처리의 일부 전환과 iOS 유지보수 인수인계를 설명합니다. 같은 서비스의 모든 기능을 한 사람이 처음부터 구현했다는 설명은 아닙니다.

사용자가 목록을 기다리는 동안 앱은 무엇을 해야 하나

앱에서 자주 묻는 질문(FAQ)을 열면 서버에서 질문과 답을 받아 목록으로 보여 줍니다. 서버 응답은 바로 오지 않을 수 있지만, 그동안 화면을 그리는 일까지 기다리게 해서는 안 됩니다. 서버를 기다리는 일과 화면에 결과를 표시하는 일을 나눠 처리해야 합니다. 이렇게 완료 시점이 다른 작업을 이어 다루는 방식을 비동기 처리라고 합니다.

기존 이력서는 Android의 오래된 작업 처리 방식인 AsyncTask를 쓰는 구조에서 사용하지 않는 메모리가 남고 네트워크 오류가 자주 발생했다고 설명합니다. 이를 RxJava 2로 바꾸며 작업·응답·오류의 흐름을 정리한 것이 이력서에 기재된 개인 경험입니다. RxJava는 시간이 걸리는 작업과 그 결과를 받는 처리를 연결하는 도구입니다. 문제·역할의 원문 범위

요청을 보내는 곳과 받은 목록을 보여 주는 곳을 나눈다

2023-10-27의 FAQ 변경에서는 이전 AsyncTask 실행 호출을 RxJava 작업 호출로 바꿨습니다. 2024-07-05 보관 코드에서 읽은 흐름은 다음과 같습니다.

  1. 서버에 질문·답 목록을 요청하고, 응답의 글자를 앱이 쓸 목록 데이터로 해석합니다.
  2. 이 작업은 Schedulers.io()라는 별도의 작업 흐름에서 실행합니다. 화면 표시를 맡는 흐름과 나누는 부분입니다.
  3. 결과를 받으면 mainThread()로 연결해 목록을 만들고 화면에 적용합니다. 이곳이 화면 스레드입니다.
  4. 결과를 전달받던 연결인 구독은 목록 처리 콜백의 끝에서 정리합니다.

코드의 fromCallable은 요청·응답 해석을 하나의 작업으로 감싸고, subscribeOn과 observeOn은 각각 작업 실행과 결과 표시를 맡는 곳을 지정합니다. 기술명 자체보다 통신을 기다린 뒤 화면을 갱신하는 순서를 코드에서 구분한 것이 이 사례의 변화입니다. FAQ 변경 커밋 · 작업·화면 반영 코드

구조를 바꿨다는 것과 모든 오류를 해결했다는 것은 다르다

이력서가 설명한 선택 이유는 작업 흐름을 단순화하고 오류 처리 위치를 정리해 운영 안정성을 높이는 것입니다. 코드에서도 통신 예외를 잡아 기록하는 부분을 읽을 수 있습니다. 그러나 이 화면의 모든 실패를 사용자에게 같은 방식으로 안내하거나 자동 재시도하는 완성된 공통 오류 처리로 확대하지 않습니다. 기존 HTTP 요청을 RxJava 작업 안에 감싼 변화와 별도 기능의 도입은 구분합니다.

구독 정리도 결과 처리가 끝나는 곳에서 합니다. 화면을 닫는 순간 요청을 취소하거나 통신 자체를 중단하는지, 이 변경으로 메모리 누수가 모두 해소됐는지는 이 코드만으로 확정할 수 없습니다. 새 구조에서도 작업을 언제 시작하고 끝낼지 관리하는 부담은 남습니다. 당시 실제 검토한 다른 기술과 배제 이유는 확보된 기록에 추가하지 않았습니다.

2023-11-20 축제 매장 상세에도 RxJava 처리를 더한 변경이 있습니다. 따라서 확인한 전환은 FAQ에만 한정되지 않지만, 앱 전체 전환 완료율을 확인한 것은 아닙니다. 기존 근거표에는 축제 지도 인증 등에 AsyncTask 클래스가 남아 있는 조회 결과도 있습니다. 일부 전환 코드를 앱 전체의 기존 구조 제거로 설명하지 않습니다. 축제 상세 변경 · 전환 범위와 남은 구조
